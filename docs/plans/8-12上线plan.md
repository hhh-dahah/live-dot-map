## 1. 这次最终要交付什么

## 2. 已确认的产品决策

以下事项不再由实施者自行改变：

- 首发系统：Windows 10/11 x64。
- 首发形态：小安装器 + 浏览器画布，不先做聊天软件，也不要求用户选择 Agent。
- 后续演进：如果人工实测证明浏览器标签页影响体验，可把同一 `app.html` 放入桌面壳；地图、本地桥和插件协议不重写。
- 正式画布：`app.html`；`canvas.html` 继续冻结，只作验收样板。
- 正式协作模式：本地桥模式；双击 HTML 只作为功能受限的降级模式。
- 数据位置：项目目录内 `.live-dot-map/`；不上传项目内容，不做遥测，不引入云数据库。
- 正式支持：Codex、Claude Code、Kimi Code 必须完成真实客户端闭环。
- 重点候选：WorkBuddy、CodeBuddy IDE/Code；真实生命周期闭环通过后才能转为正式支持。
- 通用兼容：只有 MCP 的 Agent 可以读写地图，但不能宣称保证自动注入。
- 首版检索：确定性图检索 + 本地全文检索，不使用 embedding 或云端 RAG。
- 开源范围：协议、schema、命令核心、存储桥、检索、MCP、Agent 适配器、安装器核心及对应测试使用 Apache-2.0；官网、品牌与营销资产不开放。
- 预览站和内部测试产物允许按现有工作流持续发布；公开商店提交、面向公众的下载入口切换和生产发布仍遵守发布门禁，且不作为当前开发测试的前置依赖。

## 4. 目标架构

```text
┌──────────────── 普通用户可见 ────────────────┐
│ Windows 安装器 / 启动器                       │
│   ├─ 选择项目                                 │
│   ├─ 显示 Agent 连接与信任状态                │
│   ├─ 启动、更新、修复、卸载                   │
│   └─ 自动打开浏览器 app.html                  │
│                                               │
│ 浏览器画布 app.html                           │
│   ├─ 节点、路线、标注                         │
│   ├─ 里程碑来源、层级与阅读视图               │
│   ├─ 冲突选择、历史、撤销、恢复               │
│   └─ 明确显示真实保存/协作状态                │
└──────────────────┬───────────────────────────┘
                   │ loopback HTTP + SSE
┌──────────────────▼───────────────────────────┐
│ 常驻本地桥（唯一写入权威）                    │
│   ├─ 会话、项目锁、命令验证                   │
│   ├─ WAL、原子保存、冲突、历史、恢复          │
│   ├─ 图检索、Markdown 搜索、自治门禁           │
│   └─ Agent 状态、事件广播、诊断                │
└─────────────┬───────────────────────┬────────┘
              │                       │
     .live-dot-map/             本地 MCP 代理
     map.json / Markdown               │
                                      ▼
                       Codex / Claude / Kimi
                       WorkBuddy / CodeBuddy
                       其他 MCP Agent
```

### 4.1 组件职责

#### Windows 安装器与启动器

- 安装、升级、回滚和卸载。
- 选择或注册项目，管理最近项目。
- 发现 Agent，并显示“未安装 / 已发现 / 待信任 / 已连接 / 异常”。
- 启动本地桥，等待健康检查通过后自动打开浏览器。
- 提供图形化修复，不把命令或端口暴露给用户。

#### 浏览器画布

- 只负责人类交互和状态展示，不直接承担可靠文件并发。
- 本地草稿只用于防止输入瞬间丢失；绿色“已保存”必须来自桥的持久化确认。
- 所有可见操作都转换成结构化命令。

#### 常驻本地桥

- 是 `map.json` 和协作历史的唯一写入者。
- 统一处理浏览器、人类撤销、Agent MCP、迁移和恢复。
- 身份、来源、地图规模和里程碑结构规则必须在服务端执行，不能只依赖提示词。

#### Agent 插件

- Skill/规则负责告诉 Agent 如何协作。
- Hook 或等价生命周期负责自动注入新的人类信息和当前问题相关上下文。
- MCP 负责可靠读写、ack、校验和检查点。
- Hook 失败不能改变事实状态；只有桥验证成功才显示绿色。

### 4.2 非功能目标

- 已返回保存成功的数据：RPO = 0。
- 异常重启自动恢复：RTO ≤ 30 秒。
- Agent 写入到已打开画布可见：≤ 2 秒。
- 不允许静默覆盖同字段并发修改。
- 项目内容仅保存在本机和项目目录中。
- 200 节点/400 线修改渲染 P95 ≤ 16.7ms。
- 500 节点/1000 线修改渲染 P95 ≤ 33ms。
- 1000 节点/2000 线平移缩放目标 60fps。
- 安装到首次看到项目相关地图：普通机器 ≤ 3 分钟，不要求终端操作。

### 4.3 关键架构决策与取舍

| 决策 | 采用方案 | 没有采用的方案 | 原因与代价 |
|---|---|---|---|
| 产品外壳 | 开发/RC：小安装器 + 浏览器画布；公开版：Tauri 本地协作控制台 + 同一套画布 | 纯网页壳；首版 Electron | RC 先保留浏览器以压低开发风险；公开版的控制台必须有项目选择、桥管理、Agent 状态、修复与画布能力，满足 Microsoft Store 的独立产品价值，不能只是“打开网页”。 |
| 写入架构 | 常驻本地桥是唯一写入者 | 浏览器、MCP 各自直接改文件 | 单一写入点才能统一锁、冲突、历史和事件；代价是正式协作依赖桥存活，因此必须自动拉起和恢复。 |
| 运行时与分发 | Node SEA 桥可执行文件 + Tauri；内部 RC 走 GitHub Release，公开免费版走 Microsoft Store MSIX | 要求用户安装 Node；面向公众直下未签 EXE | SEA 消除用户运行时依赖；Store 为 MSIX 提供签名、托管和更新，避免在免费产品验证期购买代码签名。代价是公开前需完成商店身份验证、元数据和审核。 |
| 数据库 | 项目内 JSON、WAL、JSONL 历史和 Markdown | SQLite、云数据库 | 延续“项目文件即记忆”、可读可迁移；代价是必须自行做好锁、日志压缩和损坏恢复。达到现有规模前不为假想扩展引入数据库。 |
| 检索 | 图结构 + BM25 确定性排序 | 云端 RAG、向量 embedding | 可离线、可解释、可测试；代价是语义召回上限较低，先用真实用户数据证明缺口后再研究下一代。 |
| Agent 连接 | 平台插件 + MCP + Hook，按能力分级 | 只写 `AGENTS.md`；只提供 MCP | 文本规则不能保证自动注入，MCP 也不定义会话生命周期；代价是必须维护多个适配器和真实客户端测试。 |
| 发布平台 | Windows x64 优先 | 首版同时覆盖 Windows/macOS/Linux | 首先把真实目标用户路径做稳；代价是首发覆盖面较小，跨平台在 Windows RC 后按同一接口扩展。 |
| 开源方式 | 核心协作层 Apache-2.0，品牌/官网私有 | 全部闭源；全仓开源 | 让本地桥和协议可审计、便于 Agent 生态适配，同时保留品牌资产；代价是需要维护公开边界和第三方 NOTICE。 |

这些决定如需改变，必须先记录原因、迁移影响和验证范围，再同步 `goal.md`；实施者不得为了局部开发方便自行更换架构。

## 6. 阶段 0：冻结基线与建立统一门禁

### 目标

先把现有大量修改整理成可审计基线，避免后面无法判断问题来自旧代码还是新修改。

### 实施内容

1. 清点当前已修改和未跟踪文件，按“v2 核心、部署产物、无关用户文件”分类。
2. 不纳入 `edgeone-login.png`、控制台快照、密钥或机器专属文件。
3. 确认 `canvas.html` 哈希与冻结版本一致。
4. 统一项目版本来源，禁止 `package.json`、CLI 和插件 manifest 分散硬编码版本。
5. 增加统一脚本：
   - `npm run verify:core`
   - `npm run verify:web`
   - `npm run verify:agents`
   - `npm run verify:installer`
   - `npm run verify:release`
6. 将目前独立运行的 E2E 纳入统一验证入口。
7. 保存当前失败基线报告，不把已知 P0 伪装成回归。

### 完成定义

- 从一个明确 commit/tag 可以重现当前 v2 构建。
- 所有源文件、生成文件和版本号可以追溯。
- CI 能区分单元测试、浏览器 E2E、Agent E2E、安装器测试和发布检查。

### 验证

- `git status --short` 中不再混有未解释的运行时文件。
- `git diff --check` 无错误。
- `canvas.html` 与冻结基线 SHA-256 相同。
- 干净临时目录克隆后能完成 `npm ci`、类型检查和现有测试。
- 删除本地生成物后重新构建，产物 hash 与 CI 产物一致。

### 阻断条件

- 发现密钥、token、用户隐私或许可来源不明的第三方代码。
- 无法从干净环境重建 `app.html` 或 `livedot.mjs`。

## 7. 阶段 1：单一写入桥与跨进程实时同步

### 依赖

阶段 0 通过。

### 目标

无论修改来自画布还是 Agent，都只通过同一个常驻桥提交，并能实时同步给另一端。

### 实施内容

1. MCP 改成桥客户端，不再在独立进程中直接 `ProjectStore.open` 后写文件。
2. 常驻桥维护每个注册项目的唯一 `ProjectStore`、文件锁和 EventHub。
3. MCP 启动时：
   - 读取项目注册信息；
   - 如果桥未运行，使用互斥锁隐藏启动；
   - 等待 `/health` 就绪；
   - 通过本地认证连接桥。
4. SSE 事件至少包含 `eventId`、`revision`、`projectId`、`actor`、影响对象和事件类型。
5. 浏览器断线重连携带 `lastEventId`；若事件窗口已经过期，主动重新取 snapshot。
6. 保留外部文件变化探测：合法外部修改先隔离解析，再形成桥命令；非法修改放入隔离副本，不污染当前图。
7. 多个桥或多个启动器同时启动时，只允许一个获得项目写锁，其余连接现有实例。

### 完成定义

- 画布、人类撤销、Agent MCP、迁移、恢复没有绕过桥的写路径。
- Agent 修改后，已打开画布无需刷新就能看到结果。
- 浏览器修改后，MCP snapshot 和下一轮检索立即可见。

### 自动验证

1. 启动桥和浏览器，再启动独立 MCP 进程创建节点；断言两秒内 DOM 出现新节点。
2. 浏览器修改节点名；MCP 查询 snapshot，断言 revision 和名称一致。
3. 浏览器与 MCP 同时改不同字段，断言自动合并且 revision 连续。
4. 双方同时改同字段，断言返回 409，冲突包含两版内容，文件没有静默覆盖。
5. 杀死桥后由 MCP 重新拉起，断言 WAL 恢复且浏览器重连收敛。
6. 同时启动两个桥，断言只有一个写入者，另一个正常连接或明确退出。

### 人工验证

- 保持画布打开，让真实 Agent 新增一个标注明确的节点；人眼确认两秒内出现、状态从接收中变成已保存。
- 断开桥后操作画布，界面只能显示离线/本地草稿，不能显示已保存；桥恢复后自动补交。

### 阻断条件

- 任一写路径仍能直接重写整个 `map.json`。
- 跨进程通知依赖用户刷新页面。
- 冲突测试出现任意一次静默覆盖。

## 8. 阶段 2：数据权限、协作历史与可靠撤销

### 依赖

阶段 1 通过。

### 目标

把“谁改的、改了什么、能不能批准、如何撤销”从提示词约定升级为服务端可靠事实。

### 实施内容

1. 客户端提交的 `actor` 只作声明；真实身份由本地桥会话绑定：
   - 浏览器授权会话 = `human`；
   - Agent 插件会话 = 指定 `agent:<id>`；
   - 迁移和恢复使用系统身份。
2. 所有 create/update/batch 路径统一通过同一权限校验器。
3. 所有节点和里程碑新增不可伪造、不可被后续覆盖的创建来源：
   - `createdBy`：`human`、`agent:<id>` 或 `migration`；
   - `milestone.origin`：`human_created` 或 `agent_created`；
   - `milestone.level`：`project`、`route` 或 `work`；
   - Agent 自主探索创建的里程碑默认必须是 `project` 或 `route` 级，不能用里程碑表达单步执行任务。
4. `milestone.status` 表示当前推进/审查状态，不表示创建权限；人和 Agent 都可以创建或更新里程碑，包括 `approved`。该状态不等于人类确认，所有来源、更新时间、更新者和变更原因必须保留并在画布可读。
5. 人类标注修改已确认内容时自动回到 `attention:new`，保留此前确认记录。
6. 新增追加式事务历史 `.live-dot-map/history/events.jsonl`：
   - `transactionId`、`commandId`、`revision`、`actor`、时间；
   - 原命令、影响对象、提交前摘要、可计算的反向命令；
   - 冲突、恢复和迁移也必须记录。
7. 每 50 个 revision 生成检查点；保留最近 20 个快速快照和最近 7 天每日备份。
8. undo/redo 改为提交反向命令：
   - 不删除原事件；
   - 不回退 revision；
   - 若对象后来被其他人修改，进入显式冲突而不是覆盖。
9. 增加历史 API 和恢复 API；恢复前自动保存当前隔离快照。

### 公共接口

- 成功提交返回：`transactionId`、`eventId`、`revision`、`affectedObjects`、`revertible`。
- `GET /api/v1/history?limit=100&before=<eventId>`。
- `POST /api/v1/history/revert`，输入目标 `transactionId` 和当前 `baseRevision`。
- `POST /api/v1/recover` 返回恢复来源、恢复前备份和新 revision。

### 完成定义

- 每个里程碑都能证明由谁创建、由谁修改，并且在画布上可一眼区分来源与层级。
- 每次已保存修改都有可查的事务记录。
- 撤销后刷新页面、重启桥、重新打开项目，结果仍然正确。

### 自动验证

1. Agent 通过 create、update、batch 创建或更新里程碑时，服务端一律写入真实 `createdBy`/`updatedBy`，伪造 `actor:human` 不得生效。
2. Agent 尝试把单步任务伪装成 `project`/`route` 里程碑，或一次创建超过数量上限的里程碑，命令被拒绝并返回压缩建议。
3. 人和 Agent 分别创建同名里程碑后，来源和时间线都保留，不能合并成来源不明的对象。
4. 连续执行 200 次操作并随机 undo/redo，重载后 snapshot 与期望状态一致。
5. 人和 Agent 先后改同一对象，撤销较早事务时不得覆盖较新的字段。
6. events.jsonl 尾部截断后自动恢复到最后完整事件。
7. 历史压缩和检查点生成后，未知扩展字段仍完整保留。

### 人工验证

- 在画布历史面板查看“我修改 / Agent 修改 / 恢复”记录，能够预览并撤销一次 Agent 操作。
- 分别由人和 Agent 创建里程碑；页面必须清楚显示创建来源、层级、最近修改人和变更时间，且人能一眼说出哪些是 Agent 新探索出来的大节点。

### 阻断条件

- undo/redo 仍只修改前端内存。
- Agent 创建里程碑后来源丢失，或能把执行碎片伪装为项目级大节点。
- 历史恢复会删除当前版本或丢失外部 Markdown。

## 9. 阶段 3：画布正式协作体验

### 依赖

阶段 1、2 通过。

### 目标

让普通用户只看界面就知道现在是否安全保存、Agent 是否读到、冲突该怎么办。

### 实施内容

1. 同步状态严格区分：
   - 本地草稿；
   - 保存中；
   - 已保存；
   - 离线待提交；
   - 冲突待选择；
   - 保存错误；
   - 降级模式。
2. 绿色“已保存”只在桥返回持久化成功后出现。
3. 新增里程碑阅读与状态面板：标准、证据、当前状态、创建来源、层级、最近变更、来源筛选和变更说明；状态操作依据实际协作权限开放给人或 Agent，不将“创建者是 Agent”误标为异常。
   - 里程碑在画布上固定使用比普通节点更大的“阶段卡”样式，不与日常执行节点混排。
   - 人创建使用“人”来源标识；Agent 创建使用“Agent 探索”来源标识；两者只表达来源，不表达高低优劣。
   - 项目级里程碑放在主路线层；路线级里程碑放在对应路线的阶段位置；工作级节点保持普通节点样式。
   - 默认总览只展示项目级和路线级里程碑；普通节点按缩放层级逐步出现，避免一打开就信息爆炸。
   - 鼠标悬停或侧栏展开后才显示创建理由、来源文档、最近变更和完整证据，主画布只保留短标题、来源和当前状态。
   - Agent 连续创建两个同层级大节点前必须先检查是否应更新/合并现有节点；一次自动探索最多新增 2 个里程碑。
4. 新增冲突比较面板：我的版本、Agent 版本、保留两者、逐字段选择。
5. 新增历史/恢复面板：最近操作、影响对象、预览、撤销、恢复备份。
6. 接入抽屉改成图形化状态，不再让普通用户复制 AGENTS 片段或手改配置。
7. 修复直开 `app.html` 对 v2 的拒绝：
   - 可浏览 v2；
   - 可导入导出 v2；
   - 浏览器本地草稿可显式下载；
   - 醒目提示“Agent 自动读取和并发保护未启用”。
8. 清理所有外部文本进入 `innerHTML` 的路径并启用 CSP。
9. 增量渲染、对象索引、rAF 合帧和视口裁剪继续作为正式性能路径。

### 完成定义

- 用户无需看文档就能区分保存失败、Agent 未读和真实成功。
- 里程碑、冲突、历史和恢复都有图形界面；人创建与 Agent 创建的大节点有稳定、易读、非污名化的视觉区分。
- 降级模式可用但绝不冒充正式协同。

### 自动验证

1. Chrome、Edge、Firefox 覆盖保存成功、离线、重连、冲突、SSE 更新和降级模式。
2. 所有可输入文本运行 XSS 载荷，断言只显示文本，不执行脚本或事件属性。
3. v2 文件在直开模式完成导入→导出→重新导入，未知字段不丢失。
4. undo/redo 每次都产生新 revision，重载仍保持结果。
5. 500/1000 对象下状态栏和审核面板不会触发全量 SVG 重建。

### 人工验证

- 非技术测试者在不解释技术名词的情况下，能够回答：是否保存、Agent 是否读取、是否有冲突、哪些大节点由人创建、哪些由 Agent 自主探索创建。
- 人为制造保存失败，测试者不会误以为已经保存。

### 阻断条件

- 任何失败状态显示绿色。
- 直开模式显示“协同正常”。
- 里程碑来源、层级或最近变更仍需编辑 JSON 才能看懂。

## 10. 阶段 4：初始地图简洁协议与项目生成

### 依赖

阶段 2、3 通过。

### 目标

首次进入时给用户一个没有负担的开始：空白画布或极简默认路线仅用于展示操作；前端清楚引导用户把一条自然语言初始化请求发给自己已有的 Agent。只有用户发起初始化后，Agent 才按简洁协议为该项目生成地图。

### 10.1 初始地图生成流程

1. 安装器注册项目后检查 `.live-dot-map/map.json`。
2. 如果已有合法地图，只打开，不覆盖、不重新生成。
3. 如果没有地图，前端让用户在两种清晰起点中选择：
   - **空白开始**：新建空地图，只显示一个轻量引导卡；
   - **查看简单示例**：加载一条默认简单路线，用于理解节点、路线和标注，且明确标识为示例，不等同于用户项目。
4. 空白或示例状态都提供主操作“让 Agent 初始化我的项目地图”：
   - 显示一条已经写好的自然语言初始化请求；支持的平台直接唤起已连接 Agent 并预填，其他平台提供一键复制后让用户粘贴发送；
   - 请求要求 Agent 先读取项目路由与核心文档，再生成项目地图；
   - 没有已连接 Agent 时，按钮显示如何连接 Agent，不编造项目内容，也不自动扫描后偷偷生成。
5. 只有用户通过该按钮或亲自向 Agent 发出等价请求后，Agent 才读取项目上下文；读取优先级为：
   - `AGENTS.md` 路由；
   - `goal.md`、PRD、README、计划和最新执行记录；
   - 用户明确指定的业务文档；
   - 最后才是源码和文件结构。
6. 用户发送初始化请求即授权 Agent 创建首张项目地图；Agent 通过桥命令直接写入，并为每个节点保留来源证据、创建者和生成理由。
7. 画布实时展示初始化进度和最终地图；历史面板允许用户随后撤销或修改，不额外增加“采用草案”的复杂步骤。
8. 初始生成绝不覆盖已有地图；若用户正在查看示例，Agent 第一次写入项目前明确提示示例会被项目地图替换。

### 10.2 初图数量规则

| 项目规模 | 建议活跃节点 | 硬上限 | 说明 |
|---|---:|---:|---|
| 小型项目 | 6–10 | 12 | 单一目标、路线清楚、上下文较少。 |
| 中型项目 | 8–12 | 15 | 多阶段或两三条当前问题路线。 |
| 大型项目 | 10–15 | 15 | 只做总览，细节进入子路线和 Markdown。 |

当用户明确要求 Agent 初始化项目地图时，生成结果必须满足：

- 只有 1 个总目标节点。
- 3–7 个关键阶段或里程碑节点；其中 Agent 自主探索创建的里程碑只允许是项目级或路线级大节点。
- 同时活跃的当前问题路线不超过 3 条。
- 每个当前问题初始待选方案不超过 2 个。
- 不为每个文件、目录、类、函数或聊天轮次建节点。
- 节点表示目标、问题、阶段、结果或审核门；方案优先表示为路线/边。
- 节点标题不超过 20 个汉字；建议控制在 6–16 个汉字。
- 标题不得使用“其他、相关内容、一些问题、继续处理”等无信息词。
- 细节、证据、长说明和来源路径写入稳定 Markdown 文件。
- 每个自动生成节点必须带 `source`、`createdBy`、生成理由和层级；无法确定的内容标记“待确认”。

### 10.3 长期简洁控制

- 单次自动探索最多新增 5 个活跃节点。
- 一个活跃节点直接待选方案最多 3 条；超过时先合并或让人选择。
- 全图活跃节点超过 20 个时提示整理。
- 全图活跃节点达到 30 个时，禁止 Agent 自动扩张，必须合并、归档或拆分路线。
- 已完成细节进入 Markdown；地图保留对决策有用的压缩结论。
- 归档和搁置默认不参与当前总览，但不删除历史。

### 完成定义

- 用户首次打开后，无须理解项目结构即可选择空白开始、看简单示例或请求 Agent 初始化。
- 用户请求初始化后，地图能在十秒内让人说清“项目要做什么、做到哪、下一步判断什么”。

### 自动验证

1. 建立小型文档项目、中型代码项目、大型混合项目三个固定夹具。
2. 断言默认空白状态不自动生成项目节点；示例路线明确带示例标识且可清空。
3. 断言用户未点击初始化前，Agent/安装器不会自动扫描项目并写入地图。
4. 断言用户请求初始化后，初图节点数、路线数、标题长度、方案分叉和里程碑层级符合规则。
5. 断言不会按目录或文件一比一建节点。
6. 断言每个生成节点能追溯到文档或被标记为待确认。
7. 已有 map 再次运行生成，文件和 revision 不变。
8. 达到 30 个活跃节点后，自动 create 命令被服务端拒绝并返回整理建议。

### 人工验证

- 新用户不看文档能找到并理解“让 Agent 初始化我的项目地图”按钮，且知道它会让自己的 Agent 读取项目后生成草案。
- 三名不了解项目的测试者在初始化完成后看图十秒，能回答目标、当前阶段和待决定事项；至少 2 人回答正确。
- 项目所有者评价“没有明显目录树化、没有关键阶段缺失、没有编造事实；Agent 创建的大节点与人创建的大节点清楚可辨”。

### 阻断条件

- 空白/示例/请求 Agent 初始化三种起点不清楚，或未请求时自动改写项目地图。
- 自动生成覆盖已有地图。
- 初图超过 15 个活跃节点或大量节点只是文件名。

## 11. 阶段 5：仿生记忆 V1 与分级自治

### 依赖

阶段 1、2、4 通过。

### 目标

让 Agent 根据当前问题从合适节点联想到全图相关因素，同时保持可解释、可离线、可测试和人类最终控制。

### 11.1 首版检索规则

不引入 embedding。候选得分统一为：

- 明确提到对象 ID 或完整名称：`+1000`。
- 新的人类标注及其目标：`+800`。
- 待审核里程碑：`+500`。
- 当前节点一跳邻居：`+300`。
- 同一路线对象：`+200`。
- 两跳邻居：`+120`。
- pending 方案：`+100`。
- 对象质量评分：加入原始 `score`。
- 最近修改：最高 `+60`，每天衰减 `5`，降到 0 为止。
- Markdown BM25：归一化为 `0–300`。
- archived、shelved 默认排除；用户明确查询历史时才加入。

每次返回：

- 最多 12 个地图对象。
- 最多 6 个 Markdown 片段。
- 每项包含来源、关系路径、得分拆解和“为什么召回”。
- 相同输入、相同 revision 必须得到确定性顺序。

### 11.2 MCP 契约

`map_next_candidates` 统一支持：

- `query`：本轮问题。
- `currentNodeId`：当前推进节点，可空。
- `limit`：1–12。
- `includeHistory`：默认 false。

`map_get_context` 返回全局推进摘要、未确认人类信息、关键里程碑及其来源/层级/状态和当前路线。

### 11.3 分级自治硬规则

只有同时满足下列条件才允许自动推进：

1. 没有未确认的人类新标注。
2. 候选在现有路线或当前节点一跳范围内。
3. 不跨越需要停下确认的 `pending`/`changes_requested` 里程碑；Agent 可以创建新的大节点里程碑，但不能借此跳过已有的关键确认点。
4. 不创建重大新方向。
5. 不删除、归档或一次批量修改超过 10 个对象。
6. 第一候选达到设定置信阈值，并显著高于第二候选。
7. 自动探索开始前已创建 pending 方案，完成后写入证据。

不满足时，只展示 1–3 个候选、理由和影响，等待人选择。以上限制必须由命令处理器再次验证，不能只写入 Skill。

### 11.4 长期仿生记忆边界

本次只交付 V1。以下方向记录到后续研究，不作为本轮完成条件：

- 类似睡眠的定期整理：合并、总结、归档和重构。
- 记忆强化、衰减、遗忘和重要性再评估。
- 跨项目但受用户授权的联想。
- 模拟人类专家的全局判断评测。
- 更长期的论文级算法设计和对照实验。

任何未来自动整理都必须先给人预览，不能静默改写人类记忆。

### 验证

1. 金丝雀测试：新标注第一、一跳高于两跳、归档默认不出现、明确历史查询可出现。
2. 跨路线 Markdown 关键词能够召回，并解释来自哪个文件片段。
3. 中文、英文、混合术语和对象 ID 分别建立固定期望排名。
4. 低置信度、未读标注、需要停下确认的里程碑、重大方向、批量 11 个对象分别测试零写入；同时验证 Agent 在安全范围内可以创建带来源的大节点里程碑。
5. 安全场景能够从正确节点创建 pending 方案、写证据并停在里程碑前。
6. 随机 1000 次检索在同一 revision 上顺序确定，不能随运行漂移。

### 阻断条件

- 自动推进仍只依赖 Agent 自觉。
- 检索结果不说明原因。
- 未读人类标注没有排在最高优先级。

## 12. 阶段 6：Agent 插件、分发与真实闭环

### 依赖

阶段 1、2、5 通过。

### 目标

把 Hook、MCP 和 Skill 包装为各平台真实可安装的插件，并用真实客户端验证，而不是只运行模拟脚本。

### 12.1 统一兼容等级

| 等级 | 必须具备 | 对外文案 |
|---|---|---|
| 完整协作 | 自动生命周期注入、MCP 读写、摘要 ID ack、Stop 闭环和真实 E2E | “完整支持” |
| 基础连接 | MCP 能可靠读写，但不能保证每次新会话自动注入 | “可连接” |
| 文件兼容 | 只能依据项目规则读取地图文件 | “协议兼容” |

界面根据实际探针显示等级，不能因为写入了配置文件就显示完整支持。

### 12.2 Codex

- 插件包含 `.codex-plugin/plugin.json`、Skill、Hooks 和 `.mcp.json`。
- 完整本地体验走：Windows 安装器配置个人 marketplace → 用户在图形界面安装 → 用户审核并信任 Hook。
- 首次 Hook 信任是官方安全边界，安装器不得静默绕过。
- 公开 Plugins Directory 的 MCP 审核要求公网生产 HTTPS MCP；活点地图坚持纯本地，因此公共目录不能作为首版完整协作链路。
- 公共目录后续只考虑引导型/Skill 型插件，是否能审核通过不作为上线依赖。
- Codex IDE extension 当前不能与完整插件体验混为一谈。

### 12.3 Claude Code

- 插件包含 `.claude-plugin/plugin.json`、Hooks、Skill 和 `.mcp.json`。
- `SessionStart` 注入全部未确认人类标注和全局摘要。
- `UserPromptSubmit` 按本轮问题重新检索。
- `Stop` 检查 ack、地图校验、冲突和未提交修改。
- 首发使用自建 GitHub marketplace，可再提交 community marketplace；官方 marketplace 收录不是上线依赖。
- 第三方 marketplace 更新默认行为需在安装时检测，不能假设自动更新已经打开。

### 12.4 Kimi Code

- 插件使用 `kimi.plugin.json`，打包 Skill、Hooks 和 MCP。
- `sessionStart.skill` 只注入静态规则，不能负责读取动态标注。
- 动态人类标注在该会话首次 `UserPromptSubmit` 查询桥并注入；后续每轮再做相关检索。
- Kimi Hook 全局 fail-open；失败时保持未确认，UI 不得显示 Agent 已读取。
- 插件当前是用户级、全项目生效，Hook 必须先检查当前 cwd 是否注册活点地图，其他项目静默退出。
- 首发通过 GitHub Release、ZIP URL 或自定义 marketplace；默认 Curated 没有公开投稿流程，不作为依赖。

### 12.5 WorkBuddy 与 CodeBuddy

- WorkBuddy 已有图形化插件、MCP、项目上下文和 Hook 基础，适合普通职场用户，应作为重点适配对象。
- 但公开资料没有证明 WorkBuddy 的 Hook 一定提供等价 `SessionStart/UserPromptSubmit/Stop` 语义，因此先实现能力探针。
- CodeBuddy IDE/Code 官方已经公开上述生命周期；CodeBuddy Code Hook 仍为 Beta，适配器必须锁定兼容版本并准备回归测试。
- 腾讯系插件打包 Skill、Hook、MCP 和本地桥启动入口；优先自建第三方 marketplace。
- WorkBuddy 真机闭环通过后升级为完整支持；否则保留基础连接，不阻塞三款首发正式 Agent。

### 12.6 通用 Agent

- 提供标准 MCP 配置、通用 Skill 和短版项目路由规则。
- MCP 标准本身不能保证“每次新会话必须自动调用工具”，也不能保证 Stop 前 ack。
- 没有生命周期 API 的平台只能标记基础连接或文件兼容。
- `AGENTS.md`/Skill 是语义约束和降级提示，不作为可靠自动注入证明。

### 12.7 Stop 闭环

每种完整支持适配器在结束前检查：

1. delivered 标注是否全部在摘要中引用并 ack。
2. 本轮实质项目修改是否同步到地图。
3. `map_validate` 是否通过。
4. 是否存在未提交命令、保存错误或冲突。
5. 是否跨越了需要停下确认的里程碑，或创建了不符合“大节点”规则的 Agent 里程碑。

第一次失败向 Agent 注入具体补救指令；第二次仍失败可允许结束，但桥记录红色“本次协作未闭环”。

### 12.8 平台事实依据

以下结论由独立子代理在 2026-08-12 按官方资料核对。平台能力可能变化，每次发布正式适配器前必须重新核对：

- Codex 插件打包与本地 MCP/Hook：[Build plugins](https://developers.openai.com/plugins/build/plugins)、[Codex Hooks](https://learn.chatgpt.com/docs/hooks)。
- Codex 公共目录提交及公网 MCP 要求：[Submit a plugin](https://developers.openai.com/plugins/deploy/submission)。
- Claude 插件结构和生命周期：[Plugins reference](https://code.claude.com/docs/en/plugins-reference)、[Hooks](https://code.claude.com/docs/en/hooks)。
- Claude 自建和第三方 marketplace：[Plugin marketplaces](https://code.claude.com/docs/en/plugin-marketplaces)。
- Kimi 插件、MCP 和 fail-open Hook：[Plugins](https://www.kimi.com/code/docs/en/kimi-code-cli/customization/plugins.html)、[MCP](https://www.kimi.com/code/docs/en/kimi-code-cli/customization/mcp.html)、[Hooks](https://www.kimi.com/code/docs/en/kimi-code-cli/customization/hooks.html)。
- WorkBuddy 图形化插件与 MCP：[插件系统](https://www.codebuddy.cn/docs/workbuddy/Plugins)、[MCP 指南](https://www.codebuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/MCP-Guide)。
- CodeBuddy 生命周期 Hook：[IDE Hooks](https://www.codebuddy.cn/docs/ide/Features/Hooks)、[Code Hooks](https://www.codebuddy.cn/docs/cli/hooks)。

官方没有明确证明的能力一律标记“未证实”，不能通过类比另一款产品或仅凭配置文件存在就升级为正式支持。

### 自动验证

- 每个适配器在隔离临时项目运行：SessionStart/首次 Prompt → 引用 ID → ack → Agent 写回 → Stop。
- Hook 崩溃、超时、退出异常和桥不可用时，标注始终保持未确认。
- MCP 只能访问注册项目根，不能通过相对路径、绝对路径或符号链接逃逸。
- 插件卸载后不再自动触发 Hook，地图数据保留。

### 真实客户端验证

Codex、Claude、Kimi 每家必须完成：

1. 全新安装或全新配置目录。
2. 图形化安装插件并完成一次官方信任确认。
3. 新建会话，人类标注 ID 出现在首次摘要。
4. Agent 调用 ack 后画布显示已读取。
5. Agent 创建节点/标注，画布两秒内更新。
6. 制造未闭环情况，Stop 第一次要求继续处理。
7. 重启客户端和电脑后仍可连接。

### 阻断条件

- 使用模拟 Hook 代替真实客户端验收。
- Hook 运行过但 ack 未成功时显示绿色。
- 对只有 MCP 的平台宣称完整自动注入。

## 13. 阶段 7：Windows 小白安装、更新和卸载

### 依赖

阶段 1–6 通过稳定接口。

### 目标

普通用户从网站下载后，只通过图形界面完成安装、选项目、连接 Agent 和打开地图。

### 13.1 分发与安装技术路线

分发不阻塞开发：先把本地桥、画布和 Agent 协作做到可验证，再按下列两条渠道生成同一套核心产物。

当前执行分叉：开发/测试继续直接运行源码和 `.deploy`，分发只在旁路生成并校验物料。SEA、NSIS、Tauri、MSIX、Partner Center 和线上健康检查属于发布门禁，不是 `npm test`、浏览器 E2E 或真实地图协议开发的前置条件。

#### A. 开发与内部 RC：GitHub Releases

- 构建 `livedot-bridge.exe`：将现有 TypeScript/JavaScript 桥构建为固定 Node SEA 可执行文件，运行机器不需要 Node。
- 构建 `活点地图-Setup-x64.exe`：可继续使用 NSIS 生成每用户测试安装包，默认安装到用户应用目录，不要求管理员权限。
- 该安装包可以暂不签名，只在项目所有者、受控测试者和私有/预发布 GitHub Release 中使用。
- Release 附 SHA-256、版本、已知限制、卸载说明和测试范围；不得把未签名 RC 作为面向陌生公众的官网下载主入口。
- RC 画布仍可由启动器打开系统浏览器，减少开发期 UI 壳的变量。

#### B. 面向普通用户的免费正式版：Microsoft Store MSIX

- 使用 Tauri 2 构建 `活点地图` 本地协作控制台，再打包为 MSIX 提交 Microsoft Store。
- 控制台负责项目选择/最近项目、本地桥启动与修复、Agent 发现与连接状态、未读标注/同步异常、更新说明和正式画布入口。
- 正式版画布可使用同一套 `app.html` 作为 Tauri WebView 内容；浏览器打开只是兼容选项，不是商店产品唯一功能。
- Microsoft Store 对提交的 MSIX 重新签名、托管下载和管理更新；因此不把自购 Authenticode 证书作为免费公开版门槛。
- Microsoft Store 开户、身份验证、商店元数据、截图、年龄分级、隐私政策和审核是公开阶段事项，不阻塞开发和内部 RC。

选择该路线的原因：

- GitHub Release 免费、透明，适合工程版本和内部测试。
- Store 分发让普通用户获得可信安装和自动更新，避免免费产品过早承担证书年费。
- Tauri 比 Electron 小；SEA 比要求用户安装 Node 可靠。
- 控制台具备本地协作价值，不是单纯把用户跳到网页，符合商店审核预期。

### 13.2 普通用户首次流程

1. RC 测试者从 GitHub Release 获取内部测试安装包；公开用户从 Microsoft Store 点击获取。
2. 双击安装或从 Store 安装，阅读权限说明并点击安装。
3. 安装完成自动打开“选择项目文件夹”。
4. 启动器自动发现已安装 Agent。
5. 用户对检测到的平台完成一次插件安装/信任；没有 Agent 也可先使用画布。
6. 已有地图直接打开；没有地图时让当前 Agent 生成草案。
7. 健康检查通过后自动打开浏览器画布。
8. 完成页只显示“开始使用”和明确的连接状态，不出现命令、JSON、端口或 Node。

### 13.3 Agent 一句话安装流程

- 网站继续提供一句自然语言接入口令。
- Agent 下载固定 GitHub Release manifest，校验 SHA-256；公开版可改为引导用户进入 Microsoft Store，而不强迫 Agent 下载未签 EXE。
- Agent 静默完成允许范围内的安装步骤；需要系统或平台信任时，把图形确认交给用户。
- Agent 不能绕过 Hook/MCP 的官方安全确认。
- 完成后直接打开画布并告诉用户“已连接哪些 Agent、还有哪一步待确认”。

### 13.4 Agent 自动发现

- 扫描 PATH、官方常见安装位置和用户级配置目录。
- 调用只读 `--version`/能力探针确认程序真实可运行。
- 只修改检测到的平台配置。
- 配置写入前逐文件备份并记录原 hash。
- 画布/启动器显示五态：未安装、已发现、待信任、已连接、异常。
- 用户后续安装新 Agent 时可点击“重新检测”。

### 13.5 快捷入口降级

1. 首选创建全局桌面快捷方式“活点地图”。
2. 桌面不可写时创建开始菜单入口。
3. 两者都不可写时，在项目内创建“打开活点地图.cmd”，同时弹窗显示准确路径和“打开所在位置”。
4. 项目有规则禁止写项目外文件时，降级不视为安装失败。
5. 多项目共用全局入口，由启动器展示最近项目；项目内入口只打开对应项目，不会重名覆盖其他项目。

### 13.6 更新与回滚

- 单一版本清单包含版本、最低兼容 schema、下载 URL、SHA-256、渠道和签名状态。
- 每天最多检查一次，只发送产品版本和系统架构，不发送项目路径或内容。
- RC 下载到临时目录后验证 SHA-256；Store 正式版由 Microsoft Store 的 MSIX 签名与交付链保证来源，启动器仍校验核心组件版本和 hash。
- 更新前备份程序版本和 Agent 配置。
- 更新后运行桥、schema、插件和画布健康检查；失败自动回滚上一版本。
- map v2 迁移先备份，程序回滚不能删除新数据。
- GitHub 的私有/预发布 RC 与 Microsoft Store Stable 分开；公开用户默认获取 Store Stable。

当前状态：版本清单、SBOM、hash 校验、无 Node SEA 桥、WinForms Setup、安装失败回滚、图形化修复/更新、卸载恢复和本地 doctor 已具备；本机 UI 自动化已看到安装、维护按钮并验证项目初始化。干净机人工验证、Store/Release 发布、真实客户端仍未完成，因此公开分发门禁仍不勾选。

### 13.7 卸载

- 删除程序、启动项、快捷方式和活点地图自己写入的插件配置。
- 根据安装时备份恢复 Agent 原配置，只撤销活点地图拥有的键，不覆盖用户后续修改。
- 默认永久保留每个项目的 `.live-dot-map/map.json`、Markdown、history 和 backup。
- 卸载界面允许用户另选“同时删除本机缓存”，但项目数据删除必须单独明确确认。

### 完成定义

- 新用户不安装 Node、不打开终端、不编辑配置就能进入正式桥模式。
- 安装失败能回滚；卸载不会破坏 Agent 原配置或项目记忆。

| 场景 | 必须结果 |

| Windows 10 x64 干净环境 | 安装、启动、打开画布成功。 |

## 14. 阶段 8：安全、故障、性能和兼容总门禁

### 依赖

阶段 1–7 全部完成。

### 14.1 安全门禁

- 本地桥只监听随机 loopback 端口。
- 一次性启动 token 只用于换取 HttpOnly、SameSite=Strict 会话。
- 校验 Host、Origin、CSRF、请求方法和内容类型。
- 会话绑定项目根和 actor 身份。
- 阻止 `..`、绝对路径、UNC、设备路径和符号链接逃逸。
- 所有文本字段只作为文本渲染，CSP 禁止内联不受信代码。
- 限制请求体、map 大小、Markdown 文件数、单文件大小和检索耗时。
- 不记录项目内容、token 或完整个人路径到发布日志。
- GitHub RC 必须提供 SHA-256 和来源说明；Microsoft Store 正式 MSIX 依赖 Store 签名与交付链；只有官网直下 EXE/MSI 才必须另行购买可信 Authenticode 签名和时间戳。

安全测试必须覆盖：

- 所有字符串字段的 XSS 载荷。
- 路径穿越和符号链接逃逸。
- 恶意 Host/Origin/CSRF。
- 伪造 actor、伪造里程碑创建来源、伪造层级和利用批量命令制造执行碎片里程碑。
- 超大 JSON、深层嵌套、压缩炸弹式输入和慢请求。
- 插件被篡改、Hook hash 变化、GitHub RC 的 hash 不匹配，以及 Store 外 EXE/MSI 的签名不匹配。

### 14.2 故障注入

| 故障 | 合格结果 |
|---|---|
| 保存时撤销目录写权限 | 不显示绿色，保留草稿，自动重试并给出可理解提示。 |
| 磁盘空间耗尽 | 当前 map 保持最后有效版本，WAL/错误状态可诊断。 |
| 写 WAL 后杀进程 | 30 秒内自动恢复到已确认命令。 |
| 临时文件写一半崩溃 | 原 map 仍合法，不出现半个 JSON。 |
| WAL 尾部损坏 | 恢复最后完整记录，损坏内容隔离。 |
| 两个写入者 | 不同字段合并，同字段显式冲突。 |
| 未来 schema | 只读打开，所有写入口断开。 |
| 外部写入损坏 JSON | 保存隔离副本，当前画布不被污染。 |
| Hook 超时或失败 | 人类标注保持未确认，不假报已读取。 |
| 桥断开 | 画布显示离线草稿，恢复后收敛。 |

### 14.3 性能门禁

- 200 节点/400 线修改渲染 P95 ≤ 16.7ms。
- 500 节点/1000 线修改渲染 P95 ≤ 33ms。
- 1000 节点/2000 线平移缩放目标 60fps，连续 30 秒无明显卡死。
- 普通项目 snapshot 和命令 API 本机 P95 ≤ 100ms。
- 1000 次确定性检索无内存持续增长，单次 P95 记录为发布基线。
- 启动器点击到桥健康目标 ≤ 2 秒；冷启动打开画布目标 ≤ 4 秒。

### 14.4 数据门禁

- 1000 次随机命令和迁移往返后 schema 有效。
- 未知字段、v1 备份、外部 Markdown 和稳定路径不丢失。
- 已返回成功的命令异常重启后全部存在，RPO = 0。
- 每个成功 commandId 重放只返回原结果，不重复产生副作用。
- 最近 20 个快照和最近 7 天每日备份策略真实执行。

### 阻断条件

- 任意 P0/P1 安全或数据问题未关闭。
- 为了通过性能测试而关闭冲突校验、历史或可靠保存。
- 只在单一浏览器、单一机器或开发者账户环境测试。

## 15. 阶段 9：开源、版本和可重复 Release

### 依赖

阶段 8 通过。

### 目标

让核心协作能力可审计、可扩展，同时确保每个公开二进制都能从明确 tag 重建和验证。

### 15.1 开源边界

公开仓库包含：

- map schema 和协议文档。
- command reducer、验证器、迁移器和冲突规则。
- WAL、原子存储、历史、恢复和检索核心。
- 本地桥 HTTP/SSE/MCP 实现。
- Codex、Claude、Kimi、腾讯系和通用适配器。
- 安装、更新、卸载核心。
- 单元、属性、故障、安全和 E2E 测试。

不公开：

- `landing/` 和官网发布配置。
- 品牌原始素材、营销图片和专有文案资产。
- 私有部署账号、密钥、控制台截图和本机配置。

许可证使用 Apache-2.0。复制或使用第三方 MIT/字体/图标内容时保留对应 LICENSE/NOTICE，构建不得无条件剥离必须保留的许可注释。

### 15.2 仓库基础文件

- `README.md`：产品价值、架构、隐私和普通安装入口。
- `LICENSE`、`NOTICE`、第三方许可清单。
- `SECURITY.md`：漏洞报告方式和支持版本。
- `CONTRIBUTING.md`：开发、测试和适配器贡献方式。
- `CHANGELOG.md`：用户可理解的变更。
- SBOM、构建来源和版本策略。

### 15.3 Release 流程

1. 从干净 tag 构建全部源码。
2. CI 运行类型、单测、属性、浏览器、Agent、安装器、安全和发布检查。
3. 生成 `app.html`、桥可执行文件、GitHub RC 安装包、Microsoft Store MSIX、插件包和校验清单。
4. GitHub RC 发布 SHA-256、SBOM、变更和已知限制；不把“未签名”隐藏成正式可信安装包。
5. 将 MSIX 通过 Partner Center 提交认证；Store 负责面向 Store 用户的包签名、托管和更新。
6. `.deploy` 只能由同一 Release 同步，不允许手工混入旧版文件。
7. 发布后逐源校验 `/app.html`、`/livedot.mjs`、`/agent-kit/setup.md` HTTP 200、版本和 hash 一致；Store 渠道额外验证安装来源、版本和更新结果。

### 完成定义

- 任意人可以从 tag 重建出内容一致的核心产物。
- 线上不会再出现 setup 已更新而 `livedot.mjs` 404 的半发布状态。
- 公开仓库不存在密钥、机器截图和许可不明资产。

### 验证

- 全历史秘密扫描无高危结果。
- 许可证扫描和 SBOM 生成通过。
- GitHub RC 的 SHA-256、SBOM 与 tag 一致；Store MSIX 的签名和身份由安装后的系统信息验证。
- 在全新机器分别只使用 GitHub RC 和 Microsoft Store 产物完成安装。
- 三个部署源逐项返回 200 且关键文件 hash 一致。

### 阻断条件

- GitHub Action “跳过部署但成功”被计为发布成功。
- 公开仓库缺许可证、NOTICE 或安全说明。
- 二进制不能追溯到唯一 tag。

## 16. 阶段 10：RC 与普通用户人工实测

### 进入条件

阶段 0–9 所有强制验证通过；`goal.md` 只能更新为“具备人工实测资格”，不能写“已正式上线”。

### RC 流程

1. 生成内部 RC 安装包和固定版本号。
2. 使用全新 Windows 用户账户和无历史浏览器状态。
3. 测试者只获得官网/下载页，不获得命令、开发文档或口头教学。
4. 完整执行以下任务：
   - 下载并安装；
   - 选择一个真实项目；
   - 选择空白/简单示例，并通过前端入口让 Agent 初始化自己的项目地图；
   - 在画布新增一条人类标注；
   - 打开新 Agent 会话并确认它优先引用该标注；
   - 让 Agent 从合适节点提出或推进方案；
   - 在画布查看一个人创建和一个 Agent 创建的里程碑，确认来源、层级和状态一眼可读；
   - 撤销一次人类或 Agent 操作；
   - 关闭并重开软件，确认数据还在；
   - 模拟一次离线或桥重启，确认状态诚实且可恢复。
5. 所有问题记录到“后端使用修改”目录，包含操作、现象、期望、严重度和截图。

### 人工实测合格条件

- 任务完成率 100%，没有 P0。
- P1 必须修复并复验；P2 可以进入公开版已知改进清单；P3 进入长期路线。
- 测试者全程没有打开终端、编辑 JSON、复制本地 URL 或理解 MCP/Hook。
- 人类标注到下一会话首次摘要引用成功率 100%。
- 测试者能正确判断保存状态、Agent 阅读状态、里程碑来源/层级和当前状态。
- 测试者主观评价初图“能看懂项目”，没有明显目录树化和信息爆炸。

### RC 迭代规则

- 修复后重新运行受影响阶段验证和阶段 8 总门禁。
- P0/P1 修复完成后进行一次对抗性审查，再用干净环境复测。
- 不允许只改 UI 文案掩盖底层未实现的状态。
