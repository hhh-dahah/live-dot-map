# GOAI 初赛 PPT — 最终架构与图片使用说明

> **用途**：本文件是给「执行 agent」（Kimi Code / Codex / Claude Code）的完整 PPT 制作指令包。按本文件逐页执行即可，无需再向用户提问。
> **提交对象**：GOAI 世界人工智能开源大赛 · Agent Infra（新智基座）赛道 · 初赛评委
> **观众画像**：多 Agent 系统 / AI 基础设施方向的技术专家；书面评审（无现场讲解）；关注「多 Agent 协同设计、Skill 工程、证据与安全可审计、开源价值」
> **风格基调**：专业产品技术展示——**大图为主、一页一观点、正文每页 ≤30 字**；克制、有证据感，不营销化；无动画堆砌，转场简洁

## 〇、全局设计规范（所有页适用）

| 项 | 规范 |
|---|---|
| 版式 | 16:9；每页 = 1 个大标题（≤14 字）+ 最多 3 条要点（每条 ≤20 字）+ 1 张主图；标题页除外 |
| 配色 | 浅色底；主色用品牌色（如项目 `brand-spec.md` 可用则读它取 OKLch 令牌）；**绿/红/灰三色仅用于方案状态语义**（绿=成功、红=失败、灰=待验证），不得用于其他装饰 |
| 字体 | 无衬线中文字体（PingFang SC / Microsoft YaHei）；标题加粗；正文 16–18pt |
| 图片 | 原图完整展示，不裁掉关键信息；加细圆角边框与轻投影；图片内文字不得被遮挡 |
| 页脚 | 每页右下角页码；左下角「活点地图 · GOAI Agent Infra」 |
| 输出 | 官方初赛模板 PPTX 或按本规范自建 PPTX；文件名 `GOAI初赛-活点地图-方案PPT.pptx` |
| 语言 | 全部简体中文 |

## 二、10 页逐页架构

### 第 1 页 · 封面
- **标题**：活点地图
- **副标题**：让人和 Agent 在同一张地图上探索未知
- **底部小字**：GOAI 世界人工智能开源大赛 · Agent Infra 赛道
- **图**：图 A 作为右侧主视觉（占版面 60%，左侧留白放标题）；或整体淡化作背景（透明度 15%）
- **备注**：封面不放其他文字

### 第 2 页 · 问题
- **标题**：为什么线性聊天不适合没有标准答案的探索任务
- **要点**（3 条）：
  1. 探索型任务天然分叉：方案并行、暂停、失败、重新比较
  2. 失败原因随会话淡忘——「为什么没选它」再难查证
  3. 换 Agent、隔几天回来，上下文要全部重讲
- **图**：无（纯文字页，可加三个竖排图标占位）

### 第 3 页 · 真实案例
- **标题**：真实场景：AI 壁纸的多路线并行探索
- **要点**：
  1. 同一目标「做出更好的壁纸」，同时探索换模型 / 换 LoRA / 改提示词 / 改工作流
  2. 路线分叉、暂停、失败、重新比较——不是线性推进
  3. 活点地图把每条路线长期保留，不淹没在聊天记录里
- **图**：无（纯文字页）

### 第 4 页 · 产品方案
- **标题**：节点、方案线、三态——一张可读的探索地图
- **要点**：
  1. 节点 = 目标 / 问题 / 结果；方案线 = 一次具体尝试
  2. 绿实线=已验证成功 · 红虚线=已验证失败 · 灰点线=待验证
  3. 路线可分叉、可悬空、可回溯；状态与连接解耦
- **图**：图 B 全幅主图（占版面 65%，图内含三态线 + 状态面板 + 评分 + 来源，一图说清方案与状态语义）
- **设计备注**：可在图上加三个小标签箭头指向绿/红/灰三处，标注「成功/失败/待验证」

### 第 5 页 · 核心创新
- **标题**：不是只读 Dashboard——人机双向操作，节点可精确寻址
- **要点**：
  1. 人可以：建节点、标注、否定方案、重选路线
  2. Agent 可以：读节点上下文、提方案、把结果写回地图
  3. 节点一键复制引用交给 Agent——新对话直接定位，无需重新描述
- **图**：图 D 全幅主图（左地图右对话的对照本身就是「寻址 → 继续探索」的可视化）
- **设计备注**：在图上对话区域加一个高亮框，标题「新对话 · 精确寻址」

### 第 6 页 · 实际 Demo / 当前完成度
- **标题**：真实使用：Agent 正在用活点地图协作
- **要点**：
  1. 截图即实拍：让 Agent「用活点地图展示项目进度」，Agent 读地图生成进度路线
  2. 五阶段推进：v2 核心完成 → 8-16 统一修复完成 → 人工验收中 → 公开发布门禁
  3. Agent 主动指出「方案详情 Markdown 缺失」——证据闭环真实生效
- **图**：图 A 全幅主图（本页是整份 PPT 的证据核心，图越大越好，可占 80%）
- **设计备注**：在右侧 Agent 回复处加红框高亮「revision 2」「缺证据提示」两处

### 第 7 页 · 技术架构
- **标题**：本地文件 + Markdown + 地图索引 + Skill/Agent 接口
- **要点**：
  1. 单一事实源：map.json 索引 + nodes/routes Markdown 分片，人机读写同一组文件
  2. 画布只放结构与状态，细节全部进 Markdown——人看极简，Agent 读全量
  3. Agent 接入：10 个固定 MCP 工具 + 官方 Skill + 四套适配器（Claude Code/Codex/Kimi Code/CodeBuddy）
- **图**：图 C 全幅主图（Markdown 详情弹窗 + 节点详情面板，正好是「概要在地图、细节在文件」的直观证据）
- **设计备注**：可在图上加标注：「节点概要（左）→ 细节文件（中）→ 结构索引（右）」

### 第 8 页 · GOAI 比赛适配
- **标题**：Planner / Executor / Verifier 三 Agent + AgentTeams 适配层
- **要点**：
  1. 三个职能 Agent：Planner 任务拆解与路线分配 · Executor 方案执行与工具调用 · Verifier 结果验证与证据检查
  2. 三 Agent 以 AgentTeams 为协同框架，经活点地图 MCP/Skill 接口共享同一份状态与证据
  3. 上下文传递=节点引用+标注送达；状态追踪=三态+里程碑+revision；证据沉淀=WAL+Markdown
- **图**：无（放一张小映射表：AgentTeams 能力 × 活点地图实现，4 行：角色编排→路线 / 任务拆解→问题路线 / 上下文传递→引用+标注 / 状态追踪→三态+revision）

### 第 9 页 · 安全 / 异常 / 人工介入
- **标题**：判断权永远在人
- **要点**：
  1. 每个对象的创建者/更新者精确可溯源：人 vs Agent（见右图「来源」字段）
  2. 危险操作确认：删除仅限人类、里程碑需人工审核，Agent 无法伪造人工确认
  3. 失败保留：失败方案不删除、可归档；WAL 全量审计，可恢复可回滚
- **图**：图 E 主图（右侧来源字段高亮框「Agent·codex创建」）
- **设计备注**：图上加一行标注：「每一个修改都可回答『谁改的、何时、依据什么』」

### 第 10 页 · 开源与下一步
- **标题**：从完整产品到多 Agent 生态
- **要点**：
  1. 下一步：完整产品打磨 → 开源发布 → AgentTeams 适配 → 多 Agent Demo
  2. 开放成果：文件协议（map.json v2）+ MCP 工具契约 + Skill 模板 + 四套适配器
  3. 长期愿景：任何 Agent，理解文件协议即可接入同一张探索地图
- **图**：无（横向四步时间轴：产品 → 开源 → AgentTeams → 多 Agent Demo）
- **结尾行**：活点地图 · 让人和 Agent 在同一张地图上探索未知（与封面呼应）

## 三、给执行 agent 的注意事项

1. **图 A 是证据核心**：第 6 页务必大图，红框高亮「revision 2」和「缺少过程证据」两处；封面用同一张图（透明淡化），全片首尾呼应
2. **图片路径**：使用上表绝对路径；若无法访问该路径，提示用户提供图片，不得用其他占位图替代
3. **第 8 页映射表**保持 4 行以内，不要展开成长表格
4. **每页要点**严格 ≤3 条、每条 ≤20 字；多写会被本规范视为不合格
5. **不添加**：动画、音效、水印、AI 生成插画、未在规范内的装饰元素
6. 完成后自查：每页 1 图（或明确无图）· 每页 ≤3 要点 · 三色仅用于状态 · 标题 ≤14 字
