# 技术架构与记忆演化

> 本文档回答两个问题：**当前工程靠什么底层技术实现核心功能**，以及**记忆系统未来往哪里演化**。
> 深入细节请跳转到文末「文档导航」列出的专项文档，本文只做整合与决策记录。

## 一句话定位

活点地图是一个本地优先的人机共享记忆工具：人把探索过程画成地图（节点=目标/问题，方案线=尝试，标注=人类指示），Agent 通过本地桥读写同一份地图文件，作为跨会话的持久记忆；历史 `result` 节点只作兼容数据。最终形态：自研单文件画布 + 轻量本地桥。

## 核心功能 → 底层技术映射

每条只讲三件事：解决什么问题、怎么实现的、为什么选这个方案。

### 1. 单一事实源：map.json v2 + Markdown 分片

- **问题**：人和 Agent 各写各的文件，必然出现两份互相矛盾的「记忆」。
- **实现**：所有结构化数据只存在于 `.live-dot-map/active-map` 指针指向的 `maps/<地图id>/map.json`；长文本细节放在 `nodes/<id>/index.md`、`routes/<id>/index.md` 及其资料包补充文件中，map.json 通过路径引用。Agent、画布、CLI 读写同一组文件，除此之外的任何副本都只是缓存。
- **为什么**：文件就是数据库，人可以直接打开看、用 Git 管、拷走备份，不需要任何服务在线。这是「本地优先」承诺的地基。
- 详见 `docs/map-json-v2.md`。

### 2. 崩溃安全：WAL + 快照 + 备份 + 隔离区

- **问题**：写文件中途断电、两个客户端同时改、外部程序把 JSON 写坏——任何一次都会丢记忆。
- **实现**：固定提交顺序 `WAL 落盘并 fsync → reducer 应用命令 → 全量校验 → 临时文件 fsync → 原子替换 → 目录 fsync → 返回新 revision`。保留最近 20 个 revision 快照和 7 天每日备份；启动时重放未完成 WAL；外部损坏的 JSON 移入 `.bridge/quarantine/` 隔离，不污染当前画布。RPO=0。
- **为什么**：这是数据库教科书级的 redo-log + 原子重命名方案，简单、可推理、可单测，比引入真正的嵌入式数据库（SQLite 等）更符合「数据即文件」的产品承诺。
- 冲突不做静默合并：`baseRevision` 落后且碰了同一字段就返回 409，双方数据都保留，交给人/Agent 显式处理。

### 3. 实时同步：SSE + 轮询降级

- **问题**：Agent 在后台改了地图，画布不能靠刷新页面才知道。
- **实现**：本地桥维护事件流（`lastEventId` 游标），画布用 Server-Sent Events 订阅；SSE 断线时自动退化为带游标的轮询。
- **为什么**：SSE 是单向推送的最简方案，无需 WebSocket 双向开销；游标轮询兜底保证任何网络环境下最终一致。

### 4. 确定性图检索：图邻域 + 状态优先级 + BM25 + 卡片索引

- **问题**：Agent 每轮会话需要「相关记忆」，但项目里没有向量数据库，也不允许引入 embedding（边界：不上云、无遥测、零依赖）。早期实现每次查询把全部 Markdown 读进内存做 BM25——节点一多，机器 IO 和内存随文件数线性膨胀（「智能索引」名不副实）。
- **实现**：双层检索——(1) **卡片索引层**（v8）：每张地图维护 `.bridge/md-index.json`，为每个 Markdown 文件登记「摘要（标题+前 300 字）+ 指纹（mtime/size/etag）+ 资产清单」，**不存全文**；查询时只对卡片做 BM25，命中才下探读取正文（`map_read_markdown`）。统计实证：500 节点地图二次查询全文读取次数 = 0，外部改动 1 个文件只重读 1 个。(2) 图邻域 + 状态优先级与早期一致（一跳邻域优先，未解决 problem > 待验证 > 历史）。返回结果附可解释的召回理由和 `autonomy` 判断。
- **卡片自愈（人机双写）**：卡片校验只用 `lstat` 廉价指纹（mtime+size），不一致即重读该文件刷新单卡；人类保存（`PUT /markdown`）、Agent 写入、改名/归档/资产变更、建节点等写路径都「保存即刷」；外部编辑器绕过桥的改动由指纹失效自动兜底；索引文件损坏时降级为按需重建。因此卡片永远不与真实文件脱节。
- **为什么**：检索结果必须对人可解释；卡片层让「索引」与「正文」分离，既满足零依赖约束，又把每次查询成本压到常数级（读 1 个索引文件 + N 次 lstat）。向量检索做不到可解释，违背零依赖约束。
- 详见 `docs/agent-protocol.md` 检索协议段。

### 5. 全局投影：上下文压缩

- **问题**：地图大了以后，把全量 JSON 塞给 Agent 会撑爆上下文，也淹没重点。
- **实现**：`map_get_context` / `map_next_candidates` 返回 `projection`——从当前地图即时计算的短摘要：目标、主路线、当前节点（stored/inferred/none）、待验证候选、最近结果、停滞路线和人类新输入。它不是第二份记忆，只是每次现算的视图；旧 milestone 字段仅兼容读取，不进入投影语义。**上下文成本控制**：Agent 每次拿到的是「节点概要（map.json）+ 卡片摘要 + 路径」，绝不包含 Markdown 全文；空 query 时兜底最近书写的摘要，带 query 时只在卡片上检索命中项。
- **为什么**：类比前额叶的工作记忆——长期记忆完整存着，每轮只把「现在要紧的」提到台前。投影规则是确定性的，人和 Agent 看到的摘要一致。

### 6. 多地图架构：一项目多任务

- **问题**（2026-08-16 前）：一个项目只能有一张地图，多个任务的记忆互相挤占。
- **实现**：`.live-dot-map/` 下 `active-map` 指针 + `maps/<id>/` 目录；每张地图自带 `nodes/`、`routes/` 和按图隔离的 `.bridge/`（wal/snapshots/backups/quarantine）。桥提供 `GET /api/v1/maps`、`POST /api/v1/maps/create|switch|rename`；切换即改写指针并切换会话与事件流。旧单图项目首次打开自动迁移（先整体备份，再迁入 `maps/default/`，旧 WAL 保留为证据文件）。
- **为什么**：一张地图 = 一个任务的记忆，Agent 默认读写当前这张；项目文件夹决定数据存哪，地图决定记忆是哪份。两级选择对应两个真实概念，文案与入口已于 8-16 定稿。

### 7. 会话闭环与人类输入注入（标注 + Markdown 双通道）

- **问题**：Agent 每次冷启动不知道人上次留了哪些话，也不知道自己该干嘛；纯靠提示词约定不可靠。且人不止在画布上留标注——节点/方案线 Markdown 正文里写的信息往往是更重要的输入，早期完全无信号，Agent 只能靠碰巧检索命中。
- **实现**：六步闭环——SessionStart hook 注入人类输入（标注 + 未确认的 Markdown 写入）→ Agent 摘要明确引用 ID → 服务端验证后标 `acknowledged` → 检索推进 → `map_apply_commands` 写回 → Stop hook 检查未闭环事项。REST、stdio 和 Agent Kit 共用固定 25 个工具、同一 dispatcher/MapManager/BundleStore/ContextDocumentProvider；写操作走命令 op 白名单（`create/update/archive/restore/set_meta/...`），同 `commandId` 幂等。
- **人类 Markdown 输入信号（v7）**：人类保存主文档（`PUT /markdown`）成功后向 `.bridge/human-md-updates.ndjson` 追加一条未确认记录（path/etag/mtime/内容摘要），Agent 每次上下文的 `humanUpdates` 与标注并列出现（`id=md:<path>`），引用后经 `map_ack_human_updates` 确认；再次修改保存会重新亮起。追加式日志、崩溃安全、按路径重放取最新状态、超限自动压缩——确保「人在图上任何位置的输入都被 Agent 留意」。
- **判断权边界**（不可协商）：Agent 自动探索受当前路线、活跃节点、标注和单批数量门槛约束；archive/restore 对人和 Agent 同权，`purge` 只允许人类二次确认或系统 30 天任务；整理建议（`map_plan_consolidation`）只读生成可逆归档命令，人确认 + checkpoint 后才原子执行。节点新写入只允许 `goal|problem`，旧 result/milestone 只保留兼容数据。Agent 无法伪造 `origin: human_created`——来源由命令处理器按会话写入。
- 详见 `docs/agent-protocol.md`。

### 8. 安全边界：稳定 origin + loopback 单例 + 会话 + CSRF + 路径白名单

- **问题**：本地 HTTP 桥如果被任意网页调用，等于把用户文件系统暴露给所有网站。
- **实现**：每个 Windows 用户只有一个常驻 Bridge，首次分配的 loopback 端口持久化并复用同一 origin；一次性令牌换 HttpOnly `SameSite=Strict` 会话 Cookie，续期同时刷新 cookie；Host/Origin 校验；有副作用的请求必须带 CSRF token；文件路径限制在项目根白名单内，拒绝绝对路径、`..`、符号链接；Markdown 上限 2 MiB，二进制附件独立上传且单文件上限 20 MiB，JSON body 上限 16 MiB。
- 详见 `docs/adr/0001-local-bridge-modular-monolith.md` 的安全边界段。

### 9. 资料包与本机能力隔离

- **实现**：对象主文档固定为 `nodes/<id>/index.md` 或 `routes/<id>/index.md`；节点创建命令提交成功即原子补建主文档（「有节点必有 index.md」，消除有记录无文件的半状态）。补充 Markdown 和附件由 BundleStore 管理，当前地图之外的文件不进入上下文。附件按扩展名、声明 MIME 和文件头校验后通过二进制流导入，SVG 强制下载。
- **资产路径化下探（v8，`map_read_asset`）**：Agent 获取附件走「路径 + 元数据」契约，桥不搬运二进制——文本类附内容，图片/PDF/Word 等二进制默认只返回路径与规格（本地 Agent 拿路径自行读取），远程 Agent 可显式 `includeContent` 取 base64。为任意格式附件建立统一下探通道，不按格式做特殊解码。
- **本机能力**：另存为、打开资料包和外部编辑器属于人类 UI 能力。浏览器只提交服务端登记的 opaque editor id，不能提交或拼接任意可执行路径；Agent 不得调用外部编辑器或文件选择器。

### 10. 单文件画布 + 模块化单体的桥

- **实现**：画布交付为单个 `app.html`（无构建、双击可用）；桥交付为无运行时 npm 依赖的单文件 `livedot.mjs`，内部按 WAL/reducer/检索/HTTP 分层但部署为一个进程。
- **为什么**（ADR-0001 的核心取舍）：本地工具的分发成本决定生死——「下载一个文件就能跑」比架构优雅重要。替代方案（纯 HTML 无桥 → 无并发保护与 Agent 写回；云端方案 → 违背本地优先）均被否决，否决理由和触发重审的条件记录在 ADR 里。

### 11. 打包分发：SEA + WinForms 单 exe

- **实现**：Node SEA 把 `livedot.mjs` 打进桥二进制；WinForms 安装器内嵌全部 payload（187 MB 单 exe），安装即解压、注册桌面快捷方式、打开画布；安装器带 `--self-check` 自检（校验 payload manifest）和版本感知更新。运行日志写 `~/.live-dot-map/logs/livedot-YYYY-MM-DD.log`，按天滚动保留 14 天，问题定位先看这里。
- 发布渠道：GitHub Release（v2.0.0 起）+ 落地页 `livedotmap.top` 的「下载 Windows 版」直链。

## 记忆系统的第一性原理

把「记忆」拆成四个过程，逐一检查现有系统缺哪块（依据：海马体索引理论 + HippoRAG / Generative Agents / Sleep-time Compute / MemoryBank / Zep / Voyager 等论文，详见 `docs/plans/2026-08-07-记忆系统演化路径研究.md`）：

| 过程 | 含义 | 当前状态 |
| --- | --- | --- |
| 编码 | 经历转成记忆 | ✅ 命令事务 + 来源/时间戳字段 |
| 索引 | 建立可检索结构 | ✅ 图结构 + kind 语义 + **卡片索引（摘要+指纹，正文不进场）** |
| 检索 | 按当下需要取回 | ✅ 投影 + 卡片 BM25 + 命中下探（500 节点二次查询全文读取=0） |
| 生命周期 | 巩固、遗忘、重组 | ⚠️ 只有整理建议的只读预览（V1 范围），自动巩固/遗忘未做 |

结论：前三块已立住，**生命周期是明确的缺口**，也是演化主线。

## 路径选择与当前位置

研究阶段评估了三条路径（详见演化路径研究文档）：

- **A. 单图深化（已选，当前所在）**：在一张策展图上做深——全局投影、失败回溯、整理例程、策展 Skill。承重墙是「整理例程」：周期性提出合并/摘要/归档/路线重组建议，人确认后执行，历史证据不丢。
- **B. 双层记忆（逃生舱，非平行选项）**：热图 + 冷存分层。触发条件只有一个——节点数稳定破千且投影实测漏信息。不是现在就做，是 A 撞墙后的升级方向。
- **C. 事件溯源（概念正确，工程不划算）**：WAL 已经是事实上的事件流；只有未来明确需要回放/归因时才把 WAL 升格为一等公民。

**A 路线 V1 已完成**（2026-08-13 定范围，8-16 前全部落地并验证）：确定性投影、当前位置、失败回溯候选、整理预览（只读）、策展 Skill、Hook/MCP 会话闭环、跨路线结构空隙检查、至少一个真实 Agent 受引导长程任务。

**V1 停止线（未完成，刻意不做）**：自动执行整理、多维评分、关联激活——这些进入仿生直觉实验线，启动前必须先有可重复的对照评测，不宣称模拟完整人脑。

## 未来升级方向

按触发条件分四层，不是排期表：

1. **A 路线收尾（近期）**：整理例程从「只读建议」走到「人确认后批量执行」的完整闭环体验优化；停滞路线与结构空隙检查的召回质量打磨。
2. **Agent 与画布项目跟随（已知缺口，v8 后记录）**：stdio Agent 桥在启动时锁定项目根，画布切换项目无通知机制（bug1，记录于「第四轮排查」图）。修复方向：桥维护全局「当前项目」指针，Agent 工具每次解析该指针，不再依赖会话 cwd。
3. **触发式升级 B（撞墙才做）**：卡片索引已把单图查询成本降到常数级；若节点稳定破千且**卡片本身**（摘要场）出现漏召回实测证据 → 热冷分层。WAL 历史已经是冷存的雏形。
4. **触发式升级 C（需要归因才做）**：需要回答「这条结论是哪次尝试得来的」时，把 WAL 从恢复机制升格为可查询的事件历史。
5. **仿生直觉研究线（长期，评测先行）**：PPR 关联激活、多维评分、周期性反思（睡眠整理）。每一步都先建对照评测再动算法；产品边界不变——人机共享、对人可见、判断权归人。
6. **分发线（与记忆无关但门禁未过）**：商店上架、代码签名、三源一致性与公开渠道门禁，按 `docs/plans/8-12上线plan.md` 推进。
