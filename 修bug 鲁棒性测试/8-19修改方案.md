## 问题 1：节点 Markdown 能用用户自己的编辑器打开（仿 Codex「打开方式」）
> 【8-20 审定：已拍板】四项全开（检测到的编辑器列表 + 用默认应用打开 + 打开所在文件夹 + 另存为）+ 检测不到时可手动选择程序 + 另存为只导出副本。细节见《8-20讨论.md》T1。
> 【8-20 第四轮修订】启动方式改为**固定参数原生启动**（ShellExecute 类），禁用拼接 `cmd /c start`；「手动选择程序」走真 Windows 文件对话框。


### 定位

- 面板里的 Markdown 路径点击后只走内置编辑器（`app.html:2692` `openMd()` → `app.html:2729` `showMdEditor()`），它就是一个全屏 `<textarea>`，没有任何粘贴图片/插入路径的能力（全文件无 paste 处理）。
- 桥端已有「在系统文件管理器中显示」端点 `POST /api/v1/markdown/reveal`（`src/bridge/server.mjs:1078`，Windows 下 `explorer /select`），但**画布 UI 从未调用它**。
- 桥端没有「用默认应用/VS Code 打开」的端点。

### 方案

面板 Markdown 行加一个「打开方式」下拉（仿 Codex，图标 + 展开）：

- **用 VS Code 打开**：桥端新增 `POST /api/v1/markdown/open`（`app: 'vscode' | 'default' | 'folder'`），`code` 不在 PATH 时回退 `%LOCALAPPDATA%\Programs\Microsoft VS Code\bin\code.cmd`，再回退默认应用。
- **用默认应用打开**：`cmd /c start "" <file>`。
- **在文件夹中显示**：复用现有 reveal 端点。
- **复制路径**：写剪贴板。

路径校验沿用 MarkdownStore 的项目根限制，不允许越界。下拉记住上次选择（localStorage），单击路径直接执行上次动作；内置 textarea 编辑器保留为「快速查看」入口。

### 改完效果

点节点 md → 默认进 VS Code（或用户选的任何编辑器），粘贴图片路径、多光标、插件全可用；内置编辑器降级为兜底。问题 13 的资料包落地后，在 VS Code 里预览 md 能直接看到图片。

## 问题 2：「设为里程碑」按钮
> 【8-20 审定：已拍板 B】里程碑整体下线；旧数据「保留但忽略」——不迁移、不主动清，旧图不报错。下线执行清单见《8-20讨论.md》T2。

## 问题 3：「语义」和「类型」重复，合并为一个
> 【8-20 审定：已拍板 A】只要 普通/问题 两态：普通=默认色圆圈、问题=红色圆圈，无蓝色、无「结果」语义；「类型」行删除；数据层 result 保留兼容，零迁移。


### 定位

- 数据模型里真正的字段是 `kind`（`goal|problem|result`，`src/shared/index.ts:6`），`type` 是旧版遗留的**纯展示字符串**，不驱动任何样式。面板把两个都显示出来（`app.html:1054-1057`），确实重复。
- 当前默认：人建节点 `type:'目标', kind:'goal'`（`app.html:1366`）；`setNodeKind()` 会把两者联动同步（`app.html:1116`）。
- 当前颜色：面板标题点 problem=红、result=**绿**（`app.html:1049`）；画布上只有 problem 有红边+「问题」徽标，result 在画布上没有专门样式。
- Agent 改 kind 本来就通（create/update 无字段白名单，kind 做枚举校验），双向可调不用额外开口。

### 方案（8-20 拍板：两态）

- 面板「语义」只露两个选项：**普通 / 问题**（底层 `kind` 数据不动，旧地图零迁移）；「类型」行从面板删除，`type` 字段保留在数据里做兼容，不再展示、不再手改。

- 人创建默认「普通」（现状即 goal，只改显示文案）；Agent 双向可改（现状已支持）。

### 改完效果

面板只剩一个两态开关，少一个易混淆字段；画布上只有两种节点：默认色、问题红。旧地图、旧 Agent 都不会炸。

## 问题 4：建立 assets 资产层（图片/PDF/Word 等非文本附件）
> 【8-20 审定：已拍板，并入问题 13】用户澄清：VS Code 粘贴图片默认落 **md 文件同目录**，且没有「nodes 必须纯 md」的要求——原 .vscode 校准方案作废。附件落盘按问题 13 拍板的资料包布局（md 同目录）执行。「不写默认提示词、人与 Agent 同一约定」的结论不变。

- 现状完全没有附件概念：桥端只允许读写项目内 `.md`（其他扩展名直接 415，`markdown-store.mjs:42`），单文件上限 2 MiB；前端没有 Markdown 渲染器，md 里写 `![](...)` 也不会显示图片。
- 你的习惯：一个问题 = 图片 + 文字描述，可能还有 word/pdf。这些文件不该塞进 map.json，也不该散在项目根。

### 方案（8-20 转向：并入问题 13）

原「每张地图一个 assets 目录」方案被 8-20 的新方向取代：附件放在节点/方案线 md 同目录（资料包），与 VS Code 粘贴默认行为天然一致。具体布局、迁移与聚合展示见「问题 13」。

保留的设计（落盘目录按 13 拍板的资料包布局执行）：

1. 桥端资产端点：`POST /api/v1/asset`（写）和 `GET /api/v1/asset?path=`（读）。扩展名白名单（png/jpg/jpeg/gif/webp/svg/pdf/doc/docx/txt/zip…），单文件上限 20 MiB，路径强制限制在当前地图目录内（防越界写）。
2. 画布内置编辑器支持**粘贴图片**：剪贴板有图 → 调端点落盘 → 光标处插入相对路径引用。
3. Agent 侧：MCP 加 `map_write_asset`（base64 写入），让 Agent 也能贴证据截图（与问题 6 的写 md 工具同一批做）。
4. `map_get_context` / `map_validate` 不变：附件不进文本检索，只被 md 引用。

## 问题 5：Codex 选了项目但没建地图就报错「无法对话」
> 【8-20 审定：敲定】补充要求：MCP 连不上时给醒目状态提醒 + 引导修复面板（与问题 9 状态条合并设计）。
> 【8-20 第四轮修订】方案 A 由「catch openStore 失败」改为**先只读检查「有效活点地图项目」**——核实发现 openStore 在空/错目录不会失败，反而会静默创建 `.live-dot-map/maps/default` 伪项目（`livedot.ts:392` → `maps.mjs:230`）。空目录/只读目录不得产生任何文件；hook 无项目静默退 0；有效项目内的真实损坏/冲突/人工停止不得被吞。


### 定位（日志 + 配置三重证据）

1. **MCP 进程崩溃会硬阻断对话**：`~/.codex/config.toml` 里我们安装器写入的 livedot-map 配置带 `required = true`（`installer.mjs:219`）——Codex 的语义是「该 MCP 启动失败就不允许对话」。
2. **崩溃点实锤**：日志里两次 `EPERM: mkdir 'C:\Program Files\WindowsApps\OpenAI.Codex_...\app\.live-dot-map'`（8-17 16:14、8-19 07:54）。MCP 不带 `--project` 时用 **cwd 当项目根**（`livedot.ts:391-394`）；Codex 裸启动（没选文件夹）时 cwd 是它自己的安装目录，只读 → `ensureMapsLayout` 第一步 mkdir 就炸 → 进程退出 → required=true → 无法对话。
3. **hooks 重复 28 次**：`~/.codex/hooks.json` 里同一个 SessionStart/UserPromptSubmit/Stop hook 各有近 10 份重复，且指向旧的 dev 路径（`dist\windows-installer\payload\...exe`），而 MCP 配置指向安装路径（`E:\livedotmap\...`）。原因：去重逻辑只认 `livedot.mjs`/`hook.cmd` 两种旧命令串（`installer.mjs:186-189`），现在写的是 exe 路径，一条都匹配不上，每次安装都叠加。每次开会话要串行跑近 10 个 30 秒超时的 hook，启动又慢又脆。
4. **反向证据**：日志显示 MCP 在 `D:\软著` 下每次都正常启动（`agent.mcp.start` 多条、无错误）。「没建地图」本身不报错——`ensureMapsLayout` 会自动建 `maps/default` 空地图（`maps.mjs:213-233`），这是刻意的零配置设计。**你遇到的报错 = cwd 不可写（裸启动）或 hook 堆积，不是「没建地图」。**

### 方案

三件套一起做：

- **A. MCP 启动永不崩**：`openStore` 失败（EPERM/只读目录等）时进程不退出，降级为「无项目模式」——`tools/list` 正常返回，`tools/call` 返回人话错误（「当前目录不可写/不是活点地图项目：<原因>」）。hook 同理，失败时静默零输出（无事不打扰原则的延伸）。
- **B. 安装器把 `required = true` 改成 `false`**：MCP 挂了只少地图能力，不挡对话。
- **C. 修 hooks 去重 + 清存量**：去重条件改成「命令里含 livedot 即视为我们的」，安装时清掉全部旧条目（含陈旧 dev 路径），统一写成当前安装位置的 exe；同时给现有用户的 hooks.json 做一次清理（安装器幂等执行即可）。

### 改完效果

Codex 裸启动、选错目录、无写权限——任何情况下都能正常对话；有地图的项目里 MCP 照常工作。会话启动不再被近 10 个重复 hook 拖慢。

## 问题 6：Agent 没有手段精确写节点 md 文档
> 【8-20 审定：通过】按原方案实施。


### 定位

- Agent 实际连的是 stdio MCP（`livedot-bridge-win-x64.exe mcp`），它只暴露 8 个工具（`livedot.ts:211-223`），**没有读写 md 的工具**——Agent 只能改 map.json 里的结构化字段，碰不到 `nodes/nX.md` 的正文。
- 但桥端 HTTP `/api/v1/mcp` 其实**已经有** `map_read_markdown` / `map_write_markdown`（`server.mjs:1155-1162`，etag 乐观锁 + 项目内路径校验 + .md 白名单）——能力存在，只是没接到 stdio MCP 这条 Agent 真正走的通道上。属于漏接，不是没做。

### 方案

把两个工具接进 stdio MCP（复用 MarkdownStore，一套校验）：

- `map_read_markdown { path }` → 返回 `{ path, content, etag }`。
- `map_write_markdown { path, content, baseEtag?, mode? }`：
  - 默认整篇替换，`baseEtag` 不一致返回 409（防覆盖别人刚写的内容）；
  - `mode: 'append'` 追加到文末——Agent 记进展最常见的动作，不用先读后写，天然无冲突。
- `path` 用 map.json 里节点/方案线的 `md` 字段值（Agent 从 `map_get_context` 能拿到），服务端强制校验必须落在项目内且以 `.md` 结尾。
- 同步更新 `agent-kit/skills/live-dot-map/SKILL.md` 和 `docs/agent-protocol.md`（工具清单 + 用法约束）。

### 改完效果

Agent 能往任意节点/方案线的 md 精确写内容：先 read 拿 etag 再 write 改全文，或一把 append 追加进展。配合问题 4 的 `map_write_asset`，「贴图 + 写字」的完整证据链人 Agent 都能做。

### 定位

### 方案选项

- **A. 完全放开（你的意见，推荐）**：删掉 `:433` 这一行拦截，Agent 与人同权。安全网靠现有快照/备份；归档/搁置的「需人审核」拦截在另一处（`:360-368`），不受影响，继续保留。
- B. 折中：Agent 只能删 `createdBy` 是 Agent 的对象，人建的仍只有人能删。保护性更强，但违反「人能做的 Agent 都能做」原则，且你明确说不需要这个协议。

### 配套改动（按 A）

- 同步改 `docs/agent-protocol.md` 和 `agent-kit/skills/live-dot-map/SKILL.md` 里「delete 仅人类」的表述。
- 附带决定（8-20 拍板）：没有「删除」只有「归档」——删节点 = 进「已归档」（md 资料包一起，文件保留），30 天自动清除；彻底删除藏在归档区二次确认，走系统回收站；入口 = 「设置」面板（仿 Codex，以后杂项也往这里收）。机制详见《8-20讨论.md》T7。

### 改完效果

Agent 测试节点、建错的节点可以自己删，不用再叫你来画布按删除键。级联、快照、日志全部沿用现成机制；被删的节点进「已归档」可找回，彻底删除才动文件、且走系统回收站多一层保险。

## 问题 8：Agent 没有新建/切换地图的入口（违反人机双向）
> 【8-20 审定：反馈未提及，默认按原方案；有异议见《8-20讨论.md》T8】。


### 定位（你的测试结论全部属实，且代码层面确认）

- stdio MCP 只有 8 个工具，无地图管理；`collection:"maps"` 会被 reducer 拒绝。
- REST `POST /api/v1/maps/create|switch` 存在但只服务画布会话（Cookie+CSRF），Agent 拿不到凭证。
- CLI 只有 install/serve/mcp/hook/doctor/uninstall。
- 误导性报错出处：`src/shared/index.ts:382`，reducer **没有 collection 白名单校验**，非法 collection 先撞 id 校验报「新对象 ID 无效」；若 id 合法还会在后面抛更难懂的 TypeError 包装。

### 方案

1. **stdio MCP 加三个工具**（内部直接复用 `maps.mjs` 的 `listMaps/createMap/writeActiveMap`，与 REST 同一组函数）：
   - `map_list` → 地图清单（id/名称/更新时间/是否当前）。

## 问题 9：没有状态栏，桥/Agent 连通性不可见，桥挂了报原始错误
> 【8-20 审定：已拍板】套二极简版：状态灯只有 🟢 正常 / 🔴 断线 两态（单机模式归入断线）；去掉「保存中」（2 秒自动保存是后台行为，状态闪来闪去反而像 bug）；断线必须弹窗，最短公式说清情况和恢复方法；恢复入口定义为用户可见的「活点地图」桌面图标，文案禁用「启动器」。定稿文案见《8-20讨论.md》T9。
> 【8-20 第四轮修订】草稿契约细化：① **断线也记 IndexedDB**（现状 `bridge-client.ts:446` 非 active 直接丢弃）；② 草稿记录含 projectId/mapId/baseRevision/基线快照/commandId（现状只存 `{value, savedAt}`）；③ 恢复 = 三方合并（旧基线/本地草稿/服务端新快照），冲突保留两边，禁止旧草稿直接覆盖 Agent 新快照；④ 稳定 origin 配套（桥优先复用上次端口，否则 IndexedDB 按 origin 隔离读不到旧草稿——`server.mjs:1228` 现为 `listen(0)` 随机端口）。


### 定位

- 现状只有一个 **8px 圆点 + 11px 灰字**（`app.html:2412`、`:2958-2962`），状态有 7 种（draft/saving/saved/offline/conflict/error/fallback），但「桥断没断、Agent 连没连」全靠把鼠标悬上去看 tooltip——等于没有。
- 桥断开时：SSE 靠浏览器原生重连，状态点变「离线」，**无 toast 无横幅**；保存失败把**原始 `error.message`** 怼进状态文案（`bridge-client.ts:510`）——普通用户看到的就是一串英文报错。
- **顺手挖出一个真数据 bug**：离线时改动会写进 IndexedDB drafts（`bridge-client.ts:450`），但**全代码没有读回路径**——刷新页面草稿就丢了，只靠 beforeunload 拦一下关闭。桥被杀 → 用户刷新 → 改动静默消失。
- SSE 重连成功后不会主动拉 snapshot 对账，断开期间的 revision 可能错过。
- Agent 活动数据现成：`GET /api/v1/agents`（health.at 最近调用时间），前端已有 `refreshAgentStatus()` 轮询，只是藏在 tooltip 里。

### 方案（8-20 拍板：两态灯 + 断线弹窗）

1. **两态灯**：🟢 正常 / 🔴 断线。「保存不到磁盘」的一切情况（桥断、会话失效、单机模式）都归入 🔴 断线。hover 小字补充：🟢「保存正常 · Agent 能看到」/ 🔴「改动暂时只存在浏览器里」。
2. **断线弹窗**：检测到断线立即弹一次（不反复弹）。文案公式：出了什么事（画布和电脑的连接断了）→ 改动没丢（你写的内容都在，恢复后会自动保存）→ 怎么恢复（主按钮「重新连接」；小字「还是连不上？双击桌面上的『活点地图』图标，再回来点这里」）。弹窗关掉后灯保持红，点红灯可再打开指引。
3. **单机模式**：归入断线，首次进入提示一次「能保存，但 Agent 看不到；双击桌面上的『活点地图』图标打开，Agent 才能看到」。
4. **修草稿不回读**（数据安全，不变）：初始化先读 IndexedDB drafts，恢复未同步改动并标示，桥恢复自动续传。
5. **SSE 重连后对账**（不变）：重连成功主动拉一次 snapshot。
6. 灯的位置与问题 12 顶栏容器一起落地，永不被遮挡；Agent 活跃信息收进 hover 小字，不占主文案。

注：恢复路径里的「活点地图」图标是安装后桌面/开始菜单的快捷方式（已核实 `installer/winforms/Program.cs:948-949`；双击 = 静默拉起后台 + 直接打开画布，全程无窗口，`Program.cs:375`）。用户看不到任何后台进程，界面文案禁止出现「启动器」「后台」「桥」这类词。

### 改完效果

用户眼里只有两种世界：🟢 一切正常、🔴 断线了——断线一定当场弹窗告诉他发生了什么、东西没丢、点哪个按钮；按钮没用时，下一步就是他能看到的那个桌面图标。刷新不丢改动，恢复自动续传。不需要懂任何技术概念。

## 问题 10：新建节点 md 打开失败「请稍后重试」（8-20 排查：会话 401 + md 路径布局错乱）
> 【8-20 审定：反馈未提及，默认按原方案；有异议见《8-20讨论.md》T8】。


### 定位（日志 + WAL + 磁盘三重证据）

- **主因是会话已死（401），不是文件问题**。桥日志 `livedot-2026-08-20.log`：03:56:49 `bridge.start`（桥在本地 11:56 重启），此后 `GET /api/v1/markdown` 连续 401（03:56:42 / 03:56:55 / 03:57:26，正是点 md 的时刻）。桥的会话是内存态（`server.mjs` 的 `sessions` Map），一重启所有已打开画布的 Cookie/CSRF 全部作废。「请稍后重试」永远没用。
- **第二个独立 bug：md 路径布局不一致，会话正常也点不开**。`map.json` 里所有节点的 md 字段是旧布局 `.live-dot-map/nodes/nX.md`（磁盘上该目录不存在），真实文件在 `.live-dot-map/maps/map-mszseg9z/nodes/`。WAL rev 19 的 touches 实锤：`nodes/n-agent-new-1/md`、`nodes/n-test-mcp/md`——人在画布拖动 n2 时，画布把 Agent 节点的 md 从 v2 路径**改写回了旧布局**。当前画布构建不认识 `maps/<id>/` 多图布局，与桥（8-18 构建）版本不一致。
- 附带：`n1.md` 在任何目录都不存在；`n3.md` 是 0 字节空文件（懒创建时机不一致）。
- 前端对失败只弹一句「Markdown 打开失败，请稍后重试」，不区分 401（会话死）/404（文件不存在）/409（冲突）。

### 方案

1. **md 路径统一为 mapDir 布局（治本）**：画布/reducer 生成 md 一律走 `stableMarkdownPath(collection, id, documentMapDir(document))`，禁止用默认 `.live-dot-map` 兜底；读取时对存量旧布局路径做兼容映射（`.live-dot-map/nodes/x.md` → `<mapDir>/nodes/x.md`，与 `maps.mjs:123` 迁移逻辑同向）。改完全量回归：人建/Agent 建/拖动/改名后 md 字段必须始终是 v2 路径。
2. **md 打开失败按原因给文案**：401 →「连接已断开，请刷新页面」；404 →「文件不存在，点这里重建」；409 →「内容被别人改过了」。禁止一律「稍后重试」。
3. 会话 401 的检测与恢复由问题 11 统一解决，本条只管路径和文案。

### 改完效果

任何来源（人/Agent/迁移）产生的节点 md 路径都指向真实文件；打开失败时用户知道是断线了还是文件丢了，不会被「稍后重试」耍。

## 问题 11：隔夜/桥重启后会话静默死亡，画布可操作但保存全丢，零提示【最严重】
> 【8-20 审定：已拍板】三件事全做：① 通行证落盘 session.json；② 滑动续期（用着就顺延）；③ 补办通道（重新连接端点）。解释与确认记录见《8-20讨论.md》T11。


### 定位（8-20 实测证据链）

- 现象：一晚上没动电脑，浏览器里的画布看着一切正常，能新建节点、能拖动，**但所有编辑都保存不上，且无任何断线提示**。新建的「assets资产层」节点核对磁盘 `map.json` 根本不存在（revision 停在 19）——要不是点 md 报错，写一天都发现不了。
- 日志实锤：桥 03:56:49 重启后，画布每 30 秒静默重试 `POST /api/v1/commands`，连续 **84 条 401** 刷了 10 分钟以上还在刷——不提醒、不放弃、不恢复。
- 根因：会话存内存（`sessions` Map），桥重启即全部失效；前端对 401 没有专门处理，只当普通失败重试。
- 与问题 9 的关系：问题 9 覆盖的是「桥进程死了」（SSE 断开能感知）；本条是**「桥活着、会话死了」**——这种失败模式前端完全无感知，是当前设计盲区。

### 方案（8-20 拍板：三件事全做）

1. **通行证落盘**：会话（sessionId + CSRF + 过期时间）写入 `.live-dot-map/.bridge/session.json`，桥重启后重新加载——旧画布标签页无感恢复。只存本机随机串，不含任何账号密码。
2. **滑动续期**：每次操作自动刷新有效期，用着就顺延；连续 7 天不用才真正过期。隔夜、周末不再是问题。
3. **补办通道**：桥端加同机 loopback「重新连接」端点。万一证真过期（比如 7 天没开），前端 401 → 进断线态（问题 9 的灯 + 弹窗），点「重新连接」自动补办新会话。
4. **401 立即显性化**：任一请求收到 401 → 停止 30 秒静默重试循环，进断线态；断开期间的本地编辑标示「未保存」，恢复后自动续传（与问题 9 草稿机制共用）。

### 改完效果

隔夜、桥重启、电脑休眠唤醒——任何场景下画布要么自动恢复继续用，要么当场弹窗告诉用户「断线了、改动没丢、点这里恢复」。杜绝「界面正常但数据在丢」这种最伤信任的状态。

## 问题 12：半屏/窄窗口下工具栏遮挡项目栏和状态区，降级/断线状态被盖住
> 【8-20 审定：敲定 A】顶栏统一容器、永不重叠。


### 定位（布局代码证据）

- 顶部两组控件**各自 `position:fixed` 定位，互不知情**：项目栏 `#project-pill` 钉在左上（`app.html:136`，`left:12px;top:12px`），工具栏 `#toolbar` 钉在顶部正中（`:139`，`left:50%;transform:translateX(-50%)`），两者同 `z-index:20`、同一 `top:12px`。DOM 里工具栏在项目栏之后（`:324` vs `:341`），**重叠时工具栏盖在上面**。
- 重叠阈值实测可算：项目栏含文件夹名 + 地图名（`.pname` 最长 180px）+ 状态点 + 菜单键，宽约 300-350px；工具栏 6 键 + 分隔约 232px。窗口宽度 < 约 950px 时两栏开始相撞——**1920 显示器半屏 = 960px，正好压线**；地图名稍长就已重叠（你的截图约 700px 宽，项目栏右半被整个盖住）。
- 唯一的响应式规则反而帮倒忙：`@media (max-width:760px)` 里 `#toolbar{max-width:calc(100vw-24px);overflow-x:auto}`（`:306`）——窄屏时工具栏直接拉满全宽居中，**保证**把项目栏盖死，项目栏本身没有任何适配。
- 被盖住的东西里就有状态：同步状态点 `#sync-dot` 是 `syncBadge()` 动态插进 `#project-pill` 的（`:2412-2418`），降级模式只改它的颜色和 tooltip（`:2400`「v2 降级模式 · 无协同保护」）。**状态被遮 = 降级/断线对用户完全隐形**，这就是你半屏用了一晚上都没发现保存失败的原因之一（与问题 9/11 互为因果）。

### 方案选项

- **A. 顶栏统一容器、永不重叠（推荐）**：项目栏 + 状态区 + 工具栏放进同一个 flex 顶栏容器，空间不足时工具栏自动换行到第二排（flex-wrap），而不是各自 fixed 赌不撞车。断点由容器实际测量决定，不受地图名长度影响。问题 9/11 要加的文字状态条作为顶栏固定成员，永远有位置、永远可见。
- B. 最小修补：加一条碰撞媒体查询（宽度 < 实测阈值时 `#toolbar{top:64px}` 下移一排），状态点从项目栏里拿出来独立固定。改动小，但阈值是拍的，地图名变长就失效。
- C. 只把状态区独立出来（合并进问题 9 的状态条，固定顶部右侧），工具栏不动。状态可见了，但项目栏被遮的问题原样保留。

推荐 A；如果要控制本期改动量，B+C 组合可作过渡，但必须删掉 `:306` 那条「拉满全宽」规则。

### 改完效果

任何窗口宽度下：项目名、地图名、连接/保存状态、核心工具都有各自位置，谁也不盖谁；半屏用户一眼能看到「降级模式/已断开」，不再靠全屏和 tooltip 猜。

## 问题 13：节点资料包——节点与方案线同构（多模态架构）
> 【8-20 审定：已拍板】用户拍板：「方案线本身跟节点一样，同等地位，架构应该是一样的。」——节点和方案线**都是资料包**（文件夹 + index.md + 附件同目录），互不嵌套；面板聚合展示问题延伸的方案线；存量一次性迁移。讨论记录见《8-20讨论.md》T13。


### 定位（代码核实）

- 节点 md 平铺 `<mapDir>/nodes/<节点id>.md`；方案线 md 平铺 `<mapDir>/routes/<方案id>.md`（方案线本来就有自己的 md，不用新建）。节点 `md` 字段是单值指针，Agent 沿指针读文件；图片无规定位置。
- 桥端 Markdown 接口只校验「项目根内 .md」，嵌套目录（如 `nodes/n3/index.md`）天然合法，协议层不用改。
- 用户习惯：VS Code 粘贴图片默认落 md 同目录——文件布局应顺应这个习惯，而不是反过来校准它。

### 方案（8-20 拍板：节点与方案线同构资料包）

- **节点资料包**：`nodes/<节点id>/index.md` 主文档 + 附件（图片/word/证据）同目录。
- **方案线资料包**：`routes/<方案id>/index.md` 主文档 + 附件同目录——与节点完全同构，方案线也能贴图、挂证据。
- 两者**互不嵌套**：方案线不搬进节点文件夹（两端连着两个节点，归属不唯一，改一次连线就得搬文件——耦合迟早乱）。「打开问题看到它的方案」由界面聚合：选中问题节点，面板列出它延伸的方案线（带 md 一键打开）。
- 附件落盘顺应 VS Code 粘贴默认（md 同目录），人/Agent/画布三方零配置一致。
- 迁移：检测到旧平铺布局一次性搬移（`n3.md` → `n3/index.md`、`e7.md` → `e7/index.md`）并改写 md 指针（与 `maps.mjs` 现有迁移逻辑同向）。
- Agent 索引零改动：md 字段还是单值指针；附件不进文本检索，只被 md 引用。
- 面板顺势做（默认并入，有异议可砍）：节点 md 区列表化——资料包里的多个 md 一排列出、可添加、可重命名（原 T13 的「多 md + UI 重命名」需求顺势覆盖）。

### 改完效果

打开一个问题/一条方案的文件夹 = 看到它的全部资料（描述、证据、图片、word）；VS Code 粘贴图片零配置落对地方；Agent 沿指针照常索引；选中问题节点，延伸方案线在面板一键即达。
