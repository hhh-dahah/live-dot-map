## 问题 A：`map_get_context` 返回 markdown 为空

### 现象
- 地图 `map-mt2hv1mh`（第三轮界面 活点地图 排查修改）实际磁盘 `nodes/n2/index.md` 有内容（`# 新节点2\n\n1112213123 2311231`），但调用 `map_get_context` 后返回 `"markdown": []`。
- 界面化的表现：Agent 新进地图看不到任何节点正文（感觉上像「没读进来」）。

### 探索发现
- `map_get_context` 的返回结构在 `src/bridge/tool-service.mjs:163`：
  ```js
  return { projectHandle, mapKey, documentId, revision, projection,
           attemptEvidence, assets: documents.assets, ...retrieved };
  ```
  其中 `markdown` 字段来自 `...retrieved`，即 `retrieveContext`（`src/shared/index.mjs:602-716`）的返回。
- `retrieveContext` 返回的 `markdown` 是 **BM25 检索命中**的结果（`src/shared/index.mjs:704-716`）：
  ```js
  const markdownScores = bm25(terms, visibleMarkdown(...));
  return { objects: ranked.slice(0, limit), markdown };
  ```
- 调用 `map_get_context` 时**没传 query** → `terms` 为空 → BM25 无命中 → `markdown: []`。
- **已用两只读调用验证链路完好**：
  1. `map_get_context(query="1112213123")` → 命中 n2（`Markdown BM25 命中`，score 300，snippet 带正文）；
  2. `map_read_markdown(node/n2/index.md)` → 直接读出全文。

### 结论
- **不是投影链路坏，是「检索语义」**：`map_get_context` 的 markdown 是“按 query 检索命中”的列表，不是“地图全量/最近书写”。
- 真正的缺口：Agent 空 query 进入地图时，拿不到任何节点正文作为默认上下文。

### 方案（待同意）
- 不改检索链路。
- 可选优化：`map_get_context`（仅 map_get_context）当 query 为空时，兜底返回「最近更新的 N 个非空 markdown + 空 query 时的全量对象」，让 Agent 一进来就能看到最新书写，而不是必须显式传 query 或用 `map_read_markdown` 定向读。
- 简单做法：在 tool-service 的 map_get_context 分支里，`if (query 为空)` 时直接返回 `documents.markdown`（collect 出的全量，已是「当前地图、非归档对象」的投影，`context-document-provider.mjs:202-326`），仅 map_next_candidates 保持检索语义。

## 问题 B：新建节点 index.md 未落盘 + 点 md 打开失败

### 现象
- 当前地图 `map.json` 记录 3 个节点（n1 新节点1 / n2 新节点2 / n3 新节点3），但磁盘 `nodes/` 下**只有 `n2/` 一个目录**，n1、n3 的 `index.md` 不存在（目录都没有）。
- 用户报：新建节点后点 md 文件 → 弹「打开失败」提示，且无状态提醒。

### 探索发现
1. **前端打开 md 是带 create 的**（装版 `app.html` 与源码一致）：
   ```js
   const result = await window.LiveDotBridge.readMarkdown(o.md, { create:true, title:o.name || '节点详情' });
   ...catch(e){ logError('markdown.open.failed', e); toast('Markdown 打开失败，请稍后重试。'); }
   ```
2. **服务端 `MarkdownStore.read(create:true)` 会自动创建目录 + index.md**（`src/bridge/markdown-store.mjs:119-152`）：文件缺失时 `mkdir + atomicWriteFile(初始内容)`。所以只要请求打到了服务端，n1/n3 就应被创建。
3. **`mapMarkdownPath` 对 bundle 布局路径原样放行**（`src/bridge/server.mjs:701-707`），不改写 `.live-dot-map/maps/<id>/nodes/<id>/index.md`，不会改坏路径。
4. **断线是第一嫌疑**：装版前端 `readMarkdown`（bridge-client.ts:496）开头：
   ```js
   if(!this.active) throw new Error('本地桥未连接，无法打开 Markdown');
   ```
   若桥会话非 active（断线/刚启动未连上），点 md 在**到达服务端之前**就抛错 → 统一被 catch 成「Markdown 打开失败」，且 n1/n3 不会被创建。这与用户当天连续的「断线、无状态提醒」现象吻合。
5. **补充发现（独立问题）**：`bundle-store.mjs:383` 的 `ensureIndex()` 全代码库**没有任何调用点**（唯一定义处 grep 无引用）。即「主文档 index.md 的标准创建入口」是死代码；实际建文件完全依赖 MarkdownStore 的懒创建，且节点 create 命令不保证原子同步创建资料包 index.md（建节点 ≠ 建文件）。

### 结论
- 静态链路通畅（create:true → MarkdownStore 自动建文件），因此 n1/n3 无文件 + 打开失败，指向**请求未到达服务端**，最可能是 `this.active=false` 的断线分支；也有小概率是项目根与会话 activeMap 不匹配。
- 需要一次「真实 UI 复现 + 看 toast 文案 + 控制台 `markdown.open.failed` 日志 / 网络面板 /api/v1/markdown 请求状态」才能 100% 钉死。

### 方案（待同意）
1. **前端断线分流**：打开失败时区分错误类型，`入口处 this.active=false` → 明确提示「未连接 / 重连」，不要笼统 toast「打开失败」；这同时对应「没有状态提醒」的投诉。
2. **建节点即建资料包**：节点 create 命令里统一调用 `bundleStore.ensureIndex`（激活这条死代码），保证「建节点 = 有 index.md」，不再依赖打开时才懒创建；顺带消除 n1/n3 这类半状态。
3. **复现一次钉死**：在你当前安装版里新建节点 → 点 md → 用 F12/控制台看 `markdown.open.failed` 与 `/api/v1/markdown?path=...&create=1` 请求状态码，能直接定位是断线分支还是服务端返回错误。

## 问题 C：人类在 md（方案线/节点）里输入的信息，Agent 不留意（2026-08-21）

### 现象
- 用户在「新节点5」的「方案1」线（e5）md 里写了 `今天上山打老虎`（磁盘 `routes/e5/index.md` 已落盘）。
- Agent 侧完全看不到这条信息：`map_get_context` 的 `humanUpdates` 里没有、`attemptEvidence` 摘要全空、只有标注 a1/a2 出现在人类更新列表。

### 探索发现
1. **检索通道是好的**：`map_get_context(query="打老虎")` 命中 e5（`Markdown BM25 命中`，snippet `# 方案1 今天上山打老虎`）。问题不在检索，在于「Agent 没有理由去 query 这些词」。
2. **`attemptEvidence` 抽不出**：e5 `hasMarkdown: true` 但 evidence/result/failureReason/nextStep 全空——抽取只认「关键证据/证据/结果/结论」等固定标题，正文不在标题下就不算数。
3. **人类 md 写入没有任何 hook**：`grep server.mjs` 确认 **没有** 任何把「人类保存 md」转成 `attention`/`ann`/human-update 的逻辑。前端 saveMarkdown（`PUT /markdown`）→ MarkdownStore.write 落盘后就结束了。
4. **对比标注（ann）通道**：人加标注自动 `attention:new` → `projection.humanUpdates` 列出 → objects 排名 860 分「人类新标注尚未确认」→ 有 `map_ack_human_updates` 确认。md 输入与标注**不对等**。

### 结论
- 不是 hook 失灵，是**「人类 md 输入」通道根本没装 hook**——人在图上任何位置的输入都应像标注一样被推给 Agent。
- 属架构级缺口：需要一条「人类 Markdown 写入 → 未确认人类输入 → Agent ack」的完整链路。

### 方案（待同意）
- **写入侧**：`PUT /markdown`（前端人类保存）成功后，追加一行 `{seq, path, etag, mtime, actor:'human', ack:false}` 到 per-map `.bridge/human-md-updates.ndjson`（追加式、崩溃安全；不进 map.json，不污染画布）。MCP 路径（Agent 自己写）不记。
- **读侧**：`map_get_context` 的 `projection.humanUpdates` 合并未 ack 的 md 条目（`id: md:<path>`，text 取正文摘要/首行）。
- **ack 侧**：`map_ack_human_updates` 支持 `md:<path>` id，ack 后从 feed 重放中剔除（按 seq 追加 ack 行；定期 compact）。
- **范围**：先覆盖主文档（`PUT /markdown`）；bundle 补充 md 的人类保存（`/bundles/markdown/replace|create|append`）后续同一机制接入。
- **兜底**：v6 的 A2（空 query 返回最近书写）已覆盖「Agent 刚进地图」场景；本方案补上「Agent 带 query 查别的事」时依然能看到人类新输入。
