路 1：图上操作（建节点、拖位置、加标注/便签）

   1. 你点一下画布 → 前端生成一条「命令」（比如 {op:create, collection:nodes, ...}）
   2. 命令发到桥 → 桥做校验 → 先追加写 WAL（.bridge/wal.ndjson，事务日志，崩溃能恢复）→
      再整份替换写 map.json
   3. map.json 就是你地图的全部结构：节点列表、方案线列表、标注(ann)列表、坐标、revision
      号

   路 2：在 md 编辑器里写字（节点正文、方案线正文）

   1. 你打开某节点/方案线的 md → 打字 → 点保存
   2. 前端调 PUT /markdown → 桥直接写磁盘文件（比如 nodes/n5/index.md、
      routes/e5/index.md）
   3. 不走 map.json、不走 WAL，就是一个独立 md 文件，写完就完事了

   Agent 怎么读到这两类数据

   Agent 每次进地图会调 map_get_context，它内部做三件事：

   1. 读 map.json → 拿到节点/线/标注，并生成一个「humanUpdates 人类更新列表」
   2. 扫磁盘 md 文件 → 把当前地图下所有对象的 index.md 读进内存
   3. 按 query 检索 → 你问什么词，它从对象名和 md 正文里找命中的

   「保证被留意」的机制，只装在路 1 上

   关键在标注（ann）上：你在画布加一个便签 → 前端写命令时自动给它打一个 attention:new 标
   记 → 于是：

   • Agent 每次 map_get_context，humanUpdates 列表里必然出现这条标注，还带「人类新标注尚
     未确认」的理由
   • Agent 看完引用它 → 调 map_ack_human_updates 说「我确认了」→ 这个 attention 变成已读
     → 下次不再刷

   这就是闭环：写入时打标记 → 读取时必列 → 确认后不再提醒。

   缺口就在路 2

   你在方案线 md 里写「今天上山打老虎」：

   • 文件落盘了 ✅
   • 但 PUT /markdown 这条路上没有任何地方给它打 attention:new ❌
   • 所以 humanUpdates 里没有它，Agent 没有任何「这里有人类新输入」的信号
   • 唯一的希望是 Agent 碰巧用 query 检索到「打老虎」这几个字——纯运气

   方案 C 补什么

   就是在路 2 上加同款三步闭环：

   1. PUT /markdown 保存成功后，往 .bridge/human-md-updates.ndjson 追加一行「未确认记录
      」（path、时间、内容摘要）——写入时打标记
   2. map_get_context 的 humanUpdates 把「未确认的 md 写入」和标注合并列出——读取时必列
   3. map_ack_human_updates 支持确认 md 条目，确认后不再提醒——确认后闭环

   三个改动点：保存 hook、读取合并、ack 支持。存储放 .bridge 下独立文件，不碰 map.json，
   不改画布。
