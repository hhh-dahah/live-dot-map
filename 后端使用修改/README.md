# 后端使用修改

> 用途：集中保存 `app.html` 完整使用测试之后的修改资料。测试记录、问题截图、录屏、样例 `map.json`、修复方案和审查结果都放在本目录，不提前散落到项目文档中。

## 当前决定

- 先不改架构，也不边测边修；先以新用户身份完整使用一遍。
- 从网站复制「一键接入」开始，只依赖页面和产品自身给出的提示；可以故意不看介绍。
- 只记录真实遇到的困惑、不顺、误操作、预期落差和失败，不要求测试者先想解决方案。
- 第一轮问题收集结束后，再统一分析产品交互、数据可靠性和技术架构，形成一份完整修改方案。
- 修改完成后依次进行：对抗性审查 → 回归测试 → 性能压测。任何一轮发现问题，都回到修复和复测，不直接宣布完成。

## 建议测试路径

1. 从营销页理解产品并复制一键接入口令。
2. 在一个全新项目里完成 Agent 接入、初始化地图和首次打开。
3. 不看额外文档，尝试新建节点、拉方案线、改状态、添加标注、编辑名称和路线。
4. 测试撤销/重做、删除、导入/导出、刷新页面、关闭后重开。
5. 连接真实项目文件夹，确认地图和 Markdown 的创建、修改与恢复。
6. 让 Agent 修改地图，同时观察画布自动刷新以及人的未保存操作是否安全。
7. 测试权限取消、文件损坏、文件夹移动、断网和误操作后的提示与恢复能力。
8. 使用真实项目连续工作一段时间，记录整体是否简单、舒服、顺手、可信。

首次真实体验请直接照着 [`人工体验验收清单.md`](人工体验验收清单.md) 做；这里保留问题记录规则，不要求测试者理解桥、WAL、MCP 或 schema。

## 每个问题怎么记录

不必写技术分析，尽量保留现场。每条至少包含：

```md
### 问题：一句话描述

- 场景：当时想完成什么
- 操作：按什么顺序做了什么
- 实际结果：看到了什么、哪里卡住
- 期望结果：下意识认为它应该怎样
- 影响：困惑 / 多走一步 / 操作失败 / 数据风险
- 频率：必现 / 偶发 / 仅一次
- 证据：截图、录屏、map.json 或相关文件路径
- 补充：当时的直觉和情绪，可不写解决方案
```

图片、录屏和测试资产后续直接放在本目录，可按需要建立 `图片/`、`录屏/`、`样例地图/`、`方案/` 等子目录。涉及真实项目隐私时，先复制并脱敏，不存密钥、Token 或 `.env`。

## 当前已知边界（不要误报成已完成）

以下是本轮自动门禁后仍然需要外部条件的事项：

1. **真实客户端信任**：Codex、Kimi Code 已有临时项目真实 CLI 闭环；Claude Code 仍需恢复可用配额后完成真实模型会话和 Hook/MCP 信任复验。
2. **WorkBuddy 生命周期**：目前只保留基础连接候选，未通过真机 SessionStart/Prompt/Stop 前不宣传完整支持。
3. **Windows 小白安装包**：内部 RC 已有无 Node WinForms 安装器、SEA 桥、修复/更新和卸载保留地图入口；干净机升级/卸载、Tauri 外壳和 Microsoft Store MSIX 仍属于公开发布门禁。
4. **公开分发**：GitHub RC、Microsoft Store MSIX、签名、审核和线上 hash/200 验证仍是发布阶段事项，不阻塞本地开发与人工走查。
5. **浏览器权限**：正式桥模式必须通过本地桥 URL 打开；双击 `app.html` 仍是明确标记的降级模式。

## 后续统一修改的验收门槛

- 用户记录的问题逐条有结论：修复、调整设计、明确不做或保留现状。
- 所有 map.json 操作符合数据协议，异常文件不能破坏原地图。（自动门禁已覆盖，仍需真实项目体验）
- 人与 Agent 同时修改时不静默丢数据。（自动门禁已覆盖，仍需真实项目体验）
- 核心操作的撤销、重做、保存、刷新和重启恢复结果一致。（自动门禁已覆盖）
- Chrome/Edge 真实文件夹授权流程、离线流程和降级导入/导出均通过。
- 对抗性审查覆盖损坏 JSON、非法引用、危险文本、快速连续操作、权限丢失和并发写入。
- 使用 20、100、200、400 节点规模进行性能测试，并记录帧耗、交互延迟和可接受上限。
