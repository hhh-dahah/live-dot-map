# 活点地图上下文架构与人机共享记忆体系

> **文档定位**：本文档基于专利申请文件《一种人机共享记忆的自愈索引与按需下探方法及系统》（`00-完整核对版.pdf`）以及代码库真实实现（`src/bridge/`、`src/shared/`、`agent-kit/`）编写，对当前系统的上下文架构、生命周期、自愈索引及减负机制进行简洁严谨的结构化梳理，作为节点 `n24` 及后续架构演进的唯一技术事实参考。

## 一、四级分层记忆架构（事实源与派生分层）

系统确立**“文件系统为唯一真实事实源（Single Source of Truth）”**原则，采用严格的四级分层，拒绝任何黑盒向量库与单体对话大文件：

```
┌─────────────────────────────────────────────────────────────┐
│ 101. 结构化地图层 (map.json)                                │
│      - 记录：节点、路线、方案边、标注、当前拓扑状态、坐标布局       │
│      - 属性：resolved, archived, status: pending/success/failed  │
└───────────────────────────┬─────────────────────────────────┘
                            │ 驱动结构投影 (105)
┌───────────────────────────▼─────────────────────────────────┐
│ 102. 卡片索引层 (.bridge/md-index.json)                     │
│      - 性质：由正文派生的轻量只读索引，严禁存储正文全文       │
│      - 条目：{ path, etag, mtimeMs, bytes, title,           │
│               summary(前300字), ownerKind, ownerId, assets }│
└───────────────────────────┬─────────────────────────────────┘
                            │ 驱动 BM25 摘要检索 (106)
┌───────────────────────────▼─────────────────────────────────┐
│ 103. 正文详情层 (nodes/<id>/index.md, routes/<id>/index.md) │
│      - 真实业务正文，人类与 Agent 共读共写的 Markdown 全文   │
│      - 规则：仅通过显式路径下探读取 (107，map_read_markdown) │
└─────────────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────────────┐
│ 104. 资产文件层 (nodes/<id>/assets/...)                     │
│      - 图片、PDF、多媒体原始文件；默认只返回元数据 (108)    │
└─────────────────────────────────────────────────────────────┘
```

## 二、两阶段访问与上下文流转（Context Pipeline）

为彻底解决 Agent 对话上下文膨胀，系统在协议层面强制切分为两个独立阶段：

### 阶段一：轻量投影与摘要检索（`map_get_context` / Hook）
1. **结构投影（Structure Projection）**：
   - 从 `map.json` 中提取当前推进节点（`currentNodeId`）、一跳/二跳拓扑邻域、活动路线、待验证方案（`pending`）以及未解决问题（`resolved !== true`）。
   - **硬上限限制**：返回结构对象严格限制在 **1 至 12 个**（默认 12），超出截断，带召回理由。
2. **卡片摘要检索（BM25 Retrieval）**：
   - 检索目标是卡片索引层（仅 300 字符摘要），**不触碰正文全文**。
   - **命中上限**：最多返回 **6 条**摘要，包含相关性得分与命中片段。
3. **人类未确认输入聚合（Human Update Log）**：
   - 读取 `.bridge/human-md-updates.ndjson`，合并未被 Agent 显式确认（`ack`）的人类保存记录。
4. **输出产物**：返回给 Agent 的是精简的拓扑骨架 + 摘要卡片列表，**单次开销极小（通常在数百至 1000 Token 内）**。

### 阶段二：显式按需下探读取（Explicit Deep Dive）
- Agent 只有在第一阶段识别到某项资料包与当前任务高度相关时，才主动调用 `map_read_markdown`。
- 此时 `bundle-store` 才按显式路径打开单文件读取正文，杜绝了“无差别全文盲目灌入”。

## 三、自愈索引机制（Self-Healing Index）

针对人类使用外部编辑器（VS Code / Typora）直接改写文件的问题，系统无需沉重的常驻文件监听守护进程，采用**查询期局部自愈校验**：

```
上下文请求发起
      │
      ▼
读取卡片索引条目，调用 fs.stat 获取目标文件当前状态
      │
      ├─── [mtime 与 bytes 均与卡片一致] ────────────────────────┐
      │                                                        │
      │ (文件未被外部改动)                                     ▼
      │                                            【零正文读取】
      │                                            直接复用卡片 300 字摘要
      │                                                        ▲
      └─── [mtime 或 bytes 不一致，或卡片不存在] ───────────────┤
           │
           ▼
     【局部自愈分支】
     仅读取该单个失效的 .md 文件全文，
     重新计算 sha256、抽取 title、生成前 300 字 summary，
     局部原子更新 .bridge/md-index.json，其余卡片不受任何影响！
```

- **验证指标**：在包含 500 个节点的大型项目中，若文件未变动，上下文检索的全文读取次数为 **0 次**；若外部修改 1 个文件，全文读取仅发生 **1 次**。

## 四、人类正文变更未确认机制（Unconfirmed Log）

为解决“人类保存了新要求，Agent 在跨会话中视而不见或遗忘”的问题：

1. **写入拦截**：人类通过应用内界面保存 Markdown 时，系统向追加式日志 `.bridge/human-md-updates.ndjson` 写入一条记录：
   `{"t":"u", "path":"...", "etag":"...", "snippet":"前160字", "ts":"..."}`
2. **会话注入**：在后续会话启动（`SessionStart`）和每次提问（`UserPromptSubmit`）时，未确认记录作为最高优先级提示持续呈现。
3. **闭环确认**：Agent 处理该要求后，调用 `map_ack_human_updates` 追加一条已确认记录：
   `{"t":"a", "path":"...", "ts":"..."}`
   日志重放时该路径不再呈现为新输入。

## 五、当前实际痛点分析与减负优化点

对照真实代码（`src/shared/index.ts`、`src/bridge/tool-service.mjs`、`src/cli/livedot.ts`），为什么实测中用户依然感知到“每次对话注入的上下文很大”？

1. **`recentMarkdown` 兜底过于慷慨**：
   当用户输入的 Prompt 较短或没有明确关键词匹配时，系统会调用 `recentMarkdown(markdownList, limit = 6)`，直接按修改时间抓取最近 6 个文档的前 320 字符塞入。
2. **已解决（`resolved`）节点降权不彻底**：
   当前代码中：
   `normalizeNodeKind(item.kind) === 'problem' && item.resolved !== true` 会增加 700 分优先级；
   但当一个问题被标为 `resolved: true` 时，它只是**没有得到那 700 分额外加分**，它仍然作为 `active` 节点留在 `map.json` 中！
   - 如果它的名称、一跳关系或 BM25 词频匹配到了 Prompt，它依然会被选入 12 个结构投影中；
   - 它的资料包依然会参与 `recentMarkdown` 的前 6 项排序；
3. **减负改造方案（与专利机制完全契合）**：
   - **已解决节点从 `recentMarkdown` 中显式剔除**：最近书写只反映未解决的任务推进，已解决节点绝不占位。
   - **已解决节点投影轻量化**：在结构投影输出中，已解决节点仅保留 `{ id, name, resolved: true, conclusion: "..." }` 一行精炼结论，绝不携带关联的富摘要片段。
   - **归档节点（Archived）保持零注入**：已归档节点在 `hiddenMarkdownPaths` 中已被完全屏蔽，继续保持严格的 100% 隔离。
