# 新节点19

 现在的方式：每个 CLI 会话肚子里都装着一整份代码

   你打开 kimi / codex 时，它会拉起一个 MCP 小进程：

   ```
     kimi CLI ──启动──> node ~/.live-dot-map/livedot.mjs mcp
                             │
                             └─ 这个文件 450KB，里面打包了【全部】工具逻辑
                                （建节点、读写 md、检索、n12 守卫……）
                                它自己直接读写你磁盘上的地图文件
   ```

   问题就出在「全部逻辑打包进这个文件，且在会话启动时加载」：

   • 我更新了代码 = 要换掉这个文件；
   • 但正在跑的 Node 进程不能换自己的代码（Windows 还会锁住运行中的文件）；
   • 所以只能请你重开会话 —— 这就是今天那步「重开 CLI」的来源。

   薄代理：小进程只当传话筒，逻辑全搬回桥里

   改完之后：

   ```
     kimi CLI ──启动──> livedot.mjs mcp（只剩几十行）
                             │  收到什么，原样转发
                             ▼
                        POST http://127.0.0.1:端口/api/v1/mcp   ← 桥进程
                             │
                             └─ 全部工具逻辑只活在这里，独此一份
   ```

   那个小进程不再懂任何业务，只做「stdin 收一行 → 发给桥 → 把桥的答复写回 stdout」。桥本来就常
   驻后台、本来就有这个 HTTP 端点（今天 canvas 和 Agent Kit 已经在走它）。

   这样「更新」就变成了：桥重启 → 新逻辑立即生效。而桥的自动重启是批次 A 已经要做的事（A2/A4）
   。传话筒文件几乎永远不用变，所以 CLI 会话永远不用为重开而重开。

   代价（说实话）

   1. 最大的代价：桥没跑的时候 agent 就没法工作。 现在的方式下，哪怕你没打开画布（桥没启动
      ），agent 也能直接读磁盘上的地图干活——今天我这个会话就是这么连上你地图的。改成薄代理后
      ，agent 调用前必须先有桥在跑。缓解办法：传话筒发现桥没起时可以自动拉起它（多写一点代码
      ），或者接受「至少开过一次画布」。我倾向前者，但这块要在 B1 里仔细做。
   2. 多一跳 HTTP。 本机回环，毫秒级，感知不到。
   3. 鉴权要重设计一小块。 桥的 /api/v1/mcp 现在防的是浏览器（会话+CSRF），传话筒是本地进程，得
      给它一个本地令牌（control.token 已存在，可复用）。不难，但属于安全面，要做对。
   4. 传话筒自己万一要改（比如协议升级），那一次还是要重开会话。但它只有几十行，这种改动几年一
      遇。

   顺带的好处

   • 现在是两个进程都能写地图（桥一份逻辑、MCP 进程一份逻辑），双写冲突的边角情况一直在累加（你
     之前测出的好几个 bug 根源都在这）。薄代理后只有桥一个写者，这类问题从根上消失。
   • 代码只用维护一份，不用再把同一套工具逻辑分别编进 bridge exe 和 livedot.mjs 两个产物。

   一句话总结：B1 = 把「每个会话自带发动机」改成「所有会话共用一个发动机」，发动机（桥）本来就
   会热重启，所以会话永远不用重开；代价是发动机熄火了车就不走，要做个自动点火。

   你看完没问题的话，我就从批次 A1 开始动手。
