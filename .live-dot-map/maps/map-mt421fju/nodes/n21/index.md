# 新节点22
## Agent 回答（2026-09-01）：部署关系速览

### 拆开看：1 个仓库，3 个地方在为你跑

```
你 git push master
   │
   ├─▶ GitHub 自己：存代码 + 当「触发器」（它不替你托管网站）
   │
   ├─▶ EdgeOne（livedotmap.top）—— 你的「门面 + 更新通道主机」
   │      平台自动从 GitHub 拉代码构建部署
   │      放：宣传页（landing）+ 更新清单 + 更新包小文件（app.html 那些）
   │      缺点：单文件 25MB 封顶，88MB 的桥 exe 放不进去
   │
   └─▶ Cloudflare Workers + CloudBase 静态托管（workflow 自动部署）
          Cloudflare：app.live-dot-map.workers.dev（备用入口）
          CloudBase：国内备用源 + 现在专门放「桥 exe」（88MB 那个，手动上传，不在自动链里）
```

### 你 push 什么会自动更新？

| 你推送的东西 | 自动生效？ |
|---|---|
| 宣传页、app.html、更新清单、小文件 | ✅ 推了 master，EdgeOne 几分钟后自动更新 |
| 88MB 桥 exe | ❌ 不自动——需要先上传到 CloudBase 再推送清单（发布脚本现状） |
| 安装包 exe（187MB） | ❌ 永远手动（GitHub Release 附件） |

不是「push 了全部生效」，而是：**推代码 → EdgeOne 自动部署「小文件」→ 用户画布自动提示更新 → 用户点更新时：小文件从 EdgeOne 下载，桥 exe 从 CloudBase 下载**。

### 免费额度与到期

- **GitHub**：公开仓库永久免费；单文件 100MB 以内能进仓库（88MB 桥 exe 正好卡在门槛下）。⚠️ 平台不建议，但能用。
- **EdgeOne / Cloudflare**：按平台免费版套餐，正常用不花钱，注意页面构建次数与请求量就行。
- **CloudBase（关键风险点）**：现在是**体验版，2026-11-19 到期**。一旦到期，桥 exe 下载会断 → 产品内更新卡死。**到期前必须换正式版（免费版套餐）或续期**。这是当前部署链路唯一的定时炸弹。

### 一句话总结

你只管 git push master；EdgeOne 自动替你更新「网站 + 更新清单 + 小文件」；桥 exe 靠每次发布时手动丢到 CloudBase；安装包手动传 GitHub Release。每月几乎零费用，唯一要盯的是 **11-19 前把 CloudBase 体验版换成正式免费版**。
## Agent 回答（2026-09-01 补充）：到底哪些是手动？商店又是怎么回事？

### 先说结论

**「每次发新版」永远有人工步骤**——这不是设计缺陷，是发版的本质：谁来定版本号、谁来打包、谁来上传大文件，都得有人按一下。自动化的目的是把「人工」压缩成「跑一条命令」，而不是消灭。

### 当前：什么自动、什么手动

| 环节 | 自动/手动 | 说明 |
|---|---|---|
| 网站、app.html、更新清单、小文件上线 | ✅ 自动 | push master，EdgeOne 自己拉自己部署 |
| **桥 exe（88MB）传 CloudBase** | ❌ 手动 | 每次发版都要传一次（脚本半自动：把上传做进发布命令后变一步） |
| **安装包 exe（187MB）传 GitHub Release** | ❌ 手动 | 永远要人工传（大小限制，进不了仓库自动链路） |
| 版本号、payloadHash、发版决定 | ❌ 手动 | 人的决策，机器不替你定 |

> 理想形态：跑一条 `npm run release:update --push` 自动完成「构建→校验→传 CloudBase→传 Release→推 GitHub」，人只负责按回车。

### 微软官方商店（MSIX）：不是「手动」而是「重新上一条链路」

- 商店**不是自动**：你要先打包成 MSIX → 上传商店开发者中心 → 填材料 → **等微软审核**（几天）→ 上架。
- 每次发新版本：**又要重新打包、重新上传、重新审核**——比现在更麻烦，不是更省事。
- 它换来的是：用户通过商店安装的版本由微软系统自动更新（不经过我们通道），**没有 SmartScreen 红屏**。
- 冲突：**商店版和我们产品内更新通道会互相打架**（商店版走微软更新，不再走我们的一键更新；两套更新器不能都在）。要上商店，得把「商店版只走商店更新」和「官网下载版走我们通道」严格分成两条线。
- 额外成本：个人开发者账户注册费约 $19 一次性 + MSIX 改造（自更新 winforms 架构要动）+ 每次发版的人工提审。

### 我的建议

先把「当前链路的手动」压成一键（发布脚本化：构建 → 验 → 传 CloudBase → 传 Release → push），商店以后再说。现在手动的部分只有 3 样：**传桥 exe、传安装包、点确认发版**——前两样都能脚本化，最后一样永远得是你。
## Agent 回答（2026-09-01 补充 2）：「codex 那种点一下更新」我们已经有，不是商店给的

### 先纠正一个观察误差

Codex「商店下载、软件里点一下更新」——你看到的那个「点一下」，**不是微软商店的功能**，是 Codex 自带的更新器（和我们的产品内一键更新是同一类东西）。微软商店如果真接管更新，体验反而是「微软后台自动静默更新，你根本不用点」。

所以：「软件内点一下」≠ 商店的价值。**这个体验活点地图已经有了**——你画布上点「立即更新」→ 自动保存 → 下载 → 桥自重启 → 画布恢复原样，就是 codex 式的体验，刚发布 v2.0.1 时我们实测过 4 轮。

### 微软商店真正提供的（和我们已有能力的对比）

| 商店带来 | 我们现状 |
|---|---|
| 第一次安装无 SmartScreen 红屏、有官方信任背书 | 官网下载安装包有红屏（点「仍要运行」） |
| 商店作为发现/分发渠道 | 官网 + GitHub 链接 |
| 商店自动静默更新（微软管） | 我们的产品内一键更新（自己管）——体验已经更好 |

### 商店的真实代价（「学它」前要看清）

1. 每次发新版：打包 MSIX → 上传 → **等微软审核几天** → 上架。发版节奏被拖慢。
2. 商店版与自更新**互斥**：商店版由微软更新，就不该再走我们的更新器；否则两套更新器打架。也就是要么「商店只做安装源、装完还是走我们通道」——但微软商店审核通常不允许这种混搭；要么商店版完全交给微软更新。
3. 个人开发者账户注册费约 $19 一次性。
4. 现架构（winforms + 自更新器）要改造为 MSIX 打包流程。

### 结论：要学的是「体验」，那个已经到手了

- **用户视角「点一下就更新」= 产品内更新** → 已实现，用户已在用，零额外成本。
- **商店**是「分发 + 信任」的可选项，不是「点一下更新」的前提；可以先不发（审核拖慢 + 互斥维护），等用户量起来、有人抱怨红屏了再上。
- **当前真正该补的**（比商店优先级高）：把发布侧的手动步骤压成一条命令（构建 → 验 → 传 CloudBase → 传 Release → push），让「发版」也变成点一下。

> 一句话：codex 的体验我们是同款，商店给的是别的（信任和渠道），要它就得付审核与互斥的账；先把发版自动化，商店放后面。
