## Agent 回答（2026-09-01）：产品形态路线——不要现在做插件化，先做到「记忆层通用」

### 结论先行

**现在做插件化是伪需求。** 插件体系解决的是「开发者生态」问题（谁来写插件、谁来贡献），不是「产品功能」问题。Obsidian 能靠插件起飞，是因为它有百万级用户 + 中立文件格式（md 本来就能被一切工具消费）+ 平台级社区。这三个前提活点地图目前一个都不占。在没有用户基础时做插件，等于造一个没有人来写的插件市场。

### 先想清楚「基础」指的是什么

这个产品的真正地基只有三件事：
1. **记录**——人和 Agent 都能以极低摩擦把任何信息放进图（节点概要 + 资料包详情）；
2. **检索**——Agent 智能索引，按需下探，不膨胀上下文；
3. **协作**——人机双写、双向同步、不丢失、不冲突。

探索场景、工作流场景、专利场景、写码场景……全都是这三件事的**用法差异**，不是结构差异。只要「记忆层」通用到极致，场景只是画布上的表达习惯。

### 分阶段方案

**阶段 1（现在→半年）：把记忆层做到「场景无关」的程度**
- 节点语义保持开放：节点=任何信息单元，路线=由你定义的秩序，标注=零切换成本的速记。不做任何场景专用的数据结构。
- 把稳定性与体验打磨到极致：架构冻结（记录/检索/协作三件事内部不再大改），更新链路可靠，上下文消耗稳定可预测。
- 检验标准：**新场景出现时，零代码变更就能用画布表达**。如果能做到，说明基础通用；如果做不到，说明是「记忆层」本身有缺口要补——这个缺口恰恰是插件化救不了的（插件不会修核心）。

**阶段 2（有场景需求持续涌入时）：用「模板 + 预设视图」承接，而不是插件体系**
- 工作流场景：内置「路线模板」（步骤卡片、状态勾选、里程碑），本质是节点/路线上的约定，不是新架构；
- 探索场景：便签墙视图、随手标注增强；
- 实现成本低（前端视图 + 少量约定字段），核心不变，也不污染项目所有用户的体验。

**阶段 3（触发条件明确后才做插件化）**
诚实地说，第一个触发信号不是「功能多」而是：
- 用户量过千、有人主动要写扩展；
- 至少 3 类场景需求不可调和（A 场景的字段与 B 场景冲突）；
- 核心已三个月没有架构级改动。
满足这些再动手：插件 = 扩展点（数据 schema 扩展 + UI 入口扩展 + Agent 工具扩展），参考 Obsidian 但核心边界比它更紧——**插件永远不能碰人机协作和索引管线**。

### 反直觉但最重要的一点

「承载的形态不一样」是正常现象，不是需要解决的问题。Obsidian 本身也没为工作流重造架构——它靠 markdown 中立性和人写的模板解决了 90% 的场景。活点地图的「人机双写 + 智能索引」已经比 Obsidian 更专注，尽量别在基础没沉之前，把复杂度引入到扩展机制上。把「记录/检索/协作」打磨到没人觉得缺东西，比发明 10 个插件扩展点有用得多。
