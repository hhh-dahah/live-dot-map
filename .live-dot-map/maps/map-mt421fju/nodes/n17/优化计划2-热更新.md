# 优化计划 2：热更新 / 更新流程简化（P0）

> 2026-08-29 经用户批准。执行策略：批次 A 先行，B 紧跟。

## 背景与目标

今天手动更新要 6 步（杀旧桥→装包→开画布→验运行时→重开 CLI 会话→清旧包），开发者都嫌复杂，普通用户更没有引导。
目标：

- **用户视角**：看到提示 → 点一下 → 画布自动重开，结束。数据无感（画布自动保存 + IndexedDB 草稿兜底，重启不丢数据）。
- **开发者视角**：一条发布命令推更新通道，不再让用户重装。

## 现状盘点（已读代码确认）

已有（比预期完整）：

- 产品内更新：`/api/v1/update/check` 与 `/api/v1/update/apply`（`src/bridge/server.mjs:769-856`，桥代发下载、逐文件 sha256 校验、失败不破坏现状）
- 更新器 `UpdateForm`（`installer/winforms/Program.cs:1330+`）：校验→复制到 `.updating`→写延迟 cmd 脚本→自身退出后切换 current→自动重开画布（1441+）
- 画布 UI：`checkForUpdate` + 菜单红点 + 确认框「更新需要重启画布，已保存的内容不会丢失」（`app.html:1685-1706`）

缺口（手动步骤的根源）：

1. **自动检查被禁用**：`app.html:1707-1715` 轮询被 `if(false)` 关死，用户永远不知道有新版本
2. **更新通道不含安装器本体**：update-manifest.files 只有 payload；UpdateForm 还把旧 exe 拷回 `.updating` → Program.cs 类改动（如 n7a）永远推不出去
3. **更新判定靠版本号**：package.json 长期 2.0.0 → `available` 永远 false
4. **单例桥复用旧代码**：装新版后若旧桥在跑，打开画布仍连旧桥；安装器只杀安装目录内进程（`Program.cs:1095-1125`），杀不到别的目录跑的桥
5. **Agent 运行时永不刷新**：`~/.live-dot-map/livedot.mjs` 只在首次 agent-kit 配置时复制（`server.mjs:307` alreadyConfigured 直接 return）；且 MCP stdio 进程内嵌全部工具逻辑，更新后必须重开 CLI 会话
6. **发布到 livedotmap.top 通道是手工步骤**

## 批次 A：一键更新闭环（用户侧零学习）

- **A1 打开自动检查**：桥就绪后静默 `checkForUpdate` 一次 + 每 6h 复查（重写被禁用的轮询为正经 setInterval）；`available` 时除菜单红点外，画布顶部出非模态提示条「新版本可用 — 立即更新 / 稍后」，点立即更新走现有 `applyUpdateFlow`
- **A2 更新通道带安装器本体**：`scripts/build-windows-installer.mjs` 的 update-manifest.files 增加 `LiveDotMapSetup.exe`（sha256+url）；`applyUpdate` 一并下载；UpdateForm 「旧 exe 拷回 .updating」兜底保持「仅当 tempRoot 无 exe 才拷」——新 exe 随 `.updating` 目录切换生效（延迟脚本在自身退出后换目录，无自覆盖问题）
- **A3 更新判定改 hash 主信号**：manifest 增加 `payloadHash`（全部文件 sha256 的组合摘要）；本地读 payload-manifest 同值比较，不等即 available；版本号只做展示，不再挡检测（bump 仍保留为发布纪律）
- **A4 消灭「手动杀桥」**：SilentOpenContext / LauncherForm 启动时读 bridge 单例状态；若运行中的桥 exe 不属于当前安装目录或版本不符 → 走控制通道（control.token）请旧桥优雅退出（复用现有 scheduleRestart 路径），再起新桥；失败才提示用户。安装器 UI 遇到「正在运行旧版」同样自动处理
- **A5 Agent 运行时同步**：`server.mjs` ensureAgentConfigured 在 `alreadyConfigured` 时也比对 `~/.live-dot-map/livedot.mjs` 与当前 runtime 的 hash，不同则复制新版（installProject 已有能力），返回 `runtimeRefreshed: true`；画布据此 toast「Agent 运行时已更新，重开 Kimi/Codex 会话后生效」

## A6 更新安全契约（2026-08-29 用户追加要求，最高优先级）

用户原话：点击更新前有提示；更新后画布自动保存、自动恢复；丢失记忆 / 无法打开是最严重 bug，一定不能出现；说到做到。

### 现有链路审计结论（读过 UpdateForm 切换脚本后）

- 已有：确认框文案「更新需要重启画布，已保存的内容不会丢失」；`.previous-*` 备份；逐文件 sha256 校验
- **缺口 a**：切换脚本 rename 完就直接启动新版并清理旧备份，**没有健康检查**——新桥起不来时不会自动回滚
- **缺口 b**：`applyUpdateFlow` 点确认后直接下载切换，**没有先强制落盘**（dirty/pending 状态可能还在 IndexedDB 草稿里）
- **缺口 c**：切换脚本当场删掉其他 `.previous-*`，备份窗口太短

### A6 契约（必须全部做到才可发布）

1. **更新前**：确认框明确「将自动保存并重启画布，地图数据不受影响」；点击后**先强制 flush**（等待同步状态变绿、无 pending），落盘失败则中止更新并明确提示
2. **更新中**：UpdateForm 逐步显示状态（已有 status 区，保持）
3. **更新后**：新桥启动 → 健康检查（桥可达 + payload 校验通过）→ 通过才清理 `.previous` 备份
4. **失败自动回滚**：新桥在限定时间内起不来 → 自动从 `.previous` 恢复旧版并打开旧版画布 + 明确提示「更新失败，已恢复原版本，地图数据未受影响」
5. **状态恢复**：重开后自动回到原项目、原地图（复用 last-project / reconnect store），尽量恢复视图位置
6. **验收必过场景**（故意破坏）：下载中途断网、切换中途杀更新器、新桥故意起不来 → 三种都必须自动回滚且地图数据字节级一致；更新后原项目/原地图自动恢复

## 执行记录：v8 假通道端到端实测（2026-08-31 凌晨）

### 结果：挖到第三个真实 bug（已修，待 v9 复测）

**bug3：更新切换失败 Access denied（current 目录被锁）**

- 现象：点「立即更新」→ 确认 → 更新器下载校验复制全部完成 → 切换脚本弹错「更新切换失败：Access to the path '…\livedotmap\current' is denied」，且弹窗模态阻塞，脚本挂起 2.5 分钟不退出；期间桥已退出，画布彻底断线，没有任何自动恢复。
- 根因（代码级实锤）：`src/bridge/server.mjs` applyUpdate 用 `spawn(updater, args, { detached, stdio:'ignore' })` **没传 cwd**，子进程继承桥的工作目录 `current/payload`。Windows 禁止重命名任何进程工作目录的祖先目录——更新器（WinForms）退出有 CLR 拆除延迟，叠加 360 杀毒实时扫描，切换脚本 2 秒后重命名 `current` 时锁还没释放，直接失败。
- 连带设计缺口：原脚本的「重命名失败」分支只弹窗提示，**不会重启旧版本画布**——用户被留在打不开的状态，恰好违反「更新失败必须恢复原样」的最高优先级契约；弹窗 `Popup` 超时参数为 0（无限等待），人不在电脑前后端流程就永久卡死。
- 修复（三处）：
  1. 桥端 spawn 更新器显式 `cwd: tempRoot`（下载目录，安装树之外），根除继承锁；
  2. 切换脚本重命名改为最多 10 次 × 3 秒重试（覆盖杀软/索引器短暂持句柄），每次失败先还原再整体重试；
  3. 彻底失败分支：先自动重启旧版本画布再弹窗，弹窗加 120 秒超时，脚本必然退出并自清理。
- 验证状态：bug 现场截图与弹窗文案已眼见为实；修复代码已改完，server 测试 35/35 过，待 v9 重建后假通道复测。
